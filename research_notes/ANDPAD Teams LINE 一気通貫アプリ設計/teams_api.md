## Q1. Which Microsoft Graph endpoints and permissions read channel messages and chat messages (list, get, replies, delta, export)?

### Takeaway
Read root channel messages with `GET /teams/{team-id}/channels/{channel-id}/messages` (replies via `/messages/{id}/replies`), chat messages with `GET /chats/{chat-id}/messages`; least-privileged **application** permissions are the resource-specific-consent (RSC) permissions `ChannelMessage.Read.Group` and `ChatMessage.Read.Chat`, with tenant-wide `ChannelMessage.Read.All` / `Chat.Read.All` as the higher-privilege (protected) alternatives. Delta exists only for a *user's* chats (`/users/{id}/chats/getAllMessages/delta`), and Graph's terms allow polling a resource only once per day, so change notifications are the intended real-time mechanism.

### Cited Findings
- `GET /teams/{team-id}/channels/{channel-id}/messages` returns the root messages of a channel **without replies**; `$top` default 20, max 50; `$expand=replies` returns up to 200 replies per message with `replies@odata.nextLink` for more; results are sorted by the last-modified date of the whole reply chain; "To list channel messages in application context, the request must be made from the tenant that the channel owner belongs to"; the API supports change notifications (page dated 10/02/2024) — [List channel messages](https://learn.microsoft.com/en-us/graph/api/channel-list-messages?view=graph-rest-1.0)
- Permissions for list channel messages (auto-generated table): Delegated least-privileged `ChannelMessage.Read.All` (higher: `Group.Read.All`, `Group.ReadWrite.All`); Application least-privileged `ChannelMessage.Read.Group` (RSC) (higher: `ChannelMessage.Read.All`, `Group.Read.All`, `Group.ReadWrite.All`); personal Microsoft accounts not supported — [List channel messages – permissions include](https://learn.microsoft.com/en-us/graph/api/channel-list-messages?view=graph-rest-1.0)
- `GET /teams/{team-id}/channels/{channel-id}/messages/{message-id}/replies` lists only the replies of the specified message; `$top` max 50; other OData parameters not supported; same permission set as list channel messages (`ChannelMessage.Read.Group` is RSC) (page dated 04/04/2024) — [List replies](https://learn.microsoft.com/en-us/graph/api/chatmessage-list-replies?view=graph-rest-1.0)
- `GET /chats/{chat-id}/messages` (also `/me/chats/{id}/messages`, `/users/{id}/chats/{id}/messages`): `$top` max 50; `$orderby` supports only `lastModifiedDateTime` (default) and `createdDateTime`, **descending only**; `$filter` on `lastModifiedDateTime` (`gt`, `lt`) and `createdDateTime` (`lt`) works only when `$orderby` is on the same property (page dated 04/04/2024) — [List messages in a chat](https://learn.microsoft.com/en-us/graph/api/chat-list-messages?view=graph-rest-1.0)
- Permissions for list chat messages: Delegated least `Chat.Read` (higher `Chat.ReadWrite`); Application least `ChatMessage.Read.Chat` (RSC) (higher `Chat.Read.All`, `Chat.ReadWrite.All`) — [List messages in a chat – permissions include](https://learn.microsoft.com/en-us/graph/api/chat-list-messages?view=graph-rest-1.0)
- Delta: `GET /users/{id | upn}/chats/getAllMessages/delta` returns messages from all chats a user participates in (1:1, group, meeting); "Delta only returns messages within the last eight months"; `$top` max 50; `$filter` supports only `lastModifiedDateTime gt`; replies are not part of this (chats have no reply threads); permissions: delegated **not supported**, application `Chat.Read.All` (least) / `Chat.ReadWrite.All` (page dated 10/08/2024) — [chatMessage: delta](https://learn.microsoft.com/en-us/graph/api/chatmessage-delta?view=graph-rest-1.0)
- Export-style bulk APIs: `GET /teams/{team-id}/channels/getAllMessages` (all public and private channels of a team; `$top`; `$filter` date range on `lastModifiedDateTime`) (page dated 04/04/2024) — [channel: getAllMessages](https://learn.microsoft.com/en-us/graph/api/channel-getallmessages?view=graph-rest-1.0); `GET /users/{id}/chats/getAllMessages` supports `$filter=from/user/userIdentityType eq '...'` (values `aadUser, onPremiseAadUser, anonymousGuest, federatedUser, personalMicrosoftAccountUser, skypeUser, phoneUser`), `$filter=from/application/applicationIdentityType eq '...'` (`aadApplication, bot, tenantBot, office365Connector, outgoingWebhook`), `from/user/id eq '{oid}'`, `messageType eq/ne 'systemEventMessage'`, joinable with `or` (page dated 05/22/2024) — [chats: getAllMessages](https://learn.microsoft.com/en-us/graph/api/chats-getallmessages?view=graph-rest-1.0)
- Polling rule: "If your app polls to see whether a resource has changed, you can only do that once per day ... If you need to hear about changes more frequently than that, you should create a subscription to that resource and receive change notifications (webhooks)"; apps that violate this are "in violation of the Microsoft APIs Terms of Use" and may be throttled further (page dated 10/02/2024) — [Use the Microsoft Graph API to work with Microsoft Teams – Polling requirements](https://learn.microsoft.com/en-us/graph/api/resources/teams-api-overview?view=graph-rest-1.0#polling-requirements)
- `chatMessage` properties relevant to age/sender logic: `from` (`application` set for bots, `user` set for people), `messageType` (`message`, `chatEvent`, `typing`, `unknownFutureValue`, `systemEventMessage` — the last needs `Prefer: include-unknown-enum-members`), `createdDateTime`, `lastModifiedDateTime` ("created ... or modified, **including when a reaction is added or removed**"), `lastEditedDateTime`, `deletedDateTime`, `replyToId` ("ID of the parent chat message or root chat message of the thread. (Only applies to chat messages in channels, not chats.)"), `chatId`, `channelIdentity`, `mentions`, `reactions`, `importance`, `eventDetail`, `webUrl` — [chatMessage resource type](https://learn.microsoft.com/en-us/graph/api/resources/chatmessage?view=graph-rest-1.0)
- Permission descriptions: `ChannelMessage.Read.All` (Application) "Allows the app to read all channel messages in Microsoft Teams"; `Chat.Read.All` (Application) "Allows the app to read all 1-to-1 or group chat messages in Microsoft Teams"; `Chat.Read.WhereInstalled` (Application) "read all one-to-one or group chat messages ... for chats where the associated Teams application is installed, without a signed-in user" — [Microsoft Graph permissions reference](https://learn.microsoft.com/en-us/graph/permissions-reference)

### Inferences
- For a per-project design (one channel or group chat per construction project), the least-privilege read path is: install a Teams app in each project team/chat with RSC `ChannelMessage.Read.Group` + `ChatMessage.Read.Chat`, then call the channel/chat message APIs app-only. No tenant-wide protected permission and no Microsoft approval form is needed on that path (see Q3).
- Because `lastModifiedDateTime` changes on reactions, "time since last message" must be computed from `createdDateTime`, and "last message" should be the newest `createdDateTime` across root messages **and** their replies (root list is sorted by reply-chain modification, not by creation).
- There is no documented v1.0 delta for channel messages in the pages read; a periodic "catch-up" sweep for channels should use `GET .../messages?$top=50` (+ replies) within throttling limits, or `channels/getAllMessages` with a `lastModifiedDateTime` window.

### Gaps
- A Microsoft Q&A thread title found by search refers to calling `/teams/{id}/channels/{id}/messages/delta` every 5–60 s; this endpoint is not in the v1.0 reference pages read here and could not be verified (search snippet) — [Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/6036630/can-a-teams-app-call-channel-messages-delta-every)
- The permission table for `GET /chatmessage` by id (`chatmessage-get`) could not be retrieved (include file 404); assume it matches list channel messages / list chat messages but verify.

## Q2. Change notifications (subscriptions) for new channel/chat messages: resource paths, permissions, expiry, lifecycle notifications, encryption, delivery rules

### Takeaway
Subscribe per channel (`/teams/{team-id}/channels/{channel-id}/messages`, app-only with RSC `ChannelMessage.Read.Group`) or per chat (`/chats/{chat-id}/messages`); a `lifecycleNotificationUrl` is mandatory for Teams resources whenever `expirationDateTime` is more than 1 hour out, the documented maximum for `chatMessage` is 4,320 minutes (3 days) in one Microsoft table but "60 minutes, renewable" in another (conflict flagged below), and rich notifications (`includeResourceData: true`) require an RSA encryption certificate plus JWT validation.

### Cited Findings
- Supported `chatMessage` resource paths and app-only permissions (page dated 11/07/2024): `/teams/getAllMessages` → Application `ChannelMessage.Read.All` (delegated not supported); `/chats/getAllMessages` → Application `Chat.Read.All`; `/teams/{team-id}/channels/{channel-id}/messages` → Delegated `ChannelMessage.Read.All`, Application `ChannelMessage.Read.Group`* or `ChannelMessage.Read.All` (RSC-marked with *), "supports including resource data in the notification in both delegated and application-only mode", supports `$search` keyword filter and a filter for messages that mention a specific user ID; `/chats/{chat-id}/messages` → Delegated `Chat.Read`, Application `ChatMessage.Read.Chat`* or `Chat.Read.All`, with the note "Permissions marked with * are supported as part of resource-specific consent for the **beta** version only currently"; `/users/{user-id}/chats/getAllMessages` → Delegated `Chat.Read`/`Chat.ReadWrite`, Application `Chat.Read.All`/`Chat.ReadWrite.All` (example shown on the beta endpoint); `/appCatalogs/teamsApps/{teams-app-id}/installedToChats/getAllMessages` → Application `Chat.Read.WhereInstalled`/`Chat.ReadWrite.WhereInstalled` — [Get change notifications for messages in Teams channels and chats](https://learn.microsoft.com/en-us/graph/teams-changenotifications-chatmessage)
- Same page: "If you request a subscription expirationDateTime that is more than 1 hour in the future, you must subscribe to lifecycle notifications by including a lifecycleNotificationUrl property ... Otherwise your subscription request will fail with ... *lifecycleNotificationUrl is a required property for subscription creation on this resource when the expirationDateTime value is set to greater than 1 hour*" — [same page](https://learn.microsoft.com/en-us/graph/teams-changenotifications-chatmessage)
- Subscription resource: `expirationDateTime` "Any value under 45 minutes after the time of the request is automatically set to 45 minutes"; `lifecycleNotificationUrl` "Required for Teams resources if the expirationDateTime value is more than 1 hour from now; optional otherwise"; `clientState` max 128 chars; `notificationUrl` must be HTTPS — [subscription resource type](https://learn.microsoft.com/en-us/graph/api/resources/subscription?view=graph-rest-1.0)
- Maximum subscription lifetime table: Teams `chatMessage` 4,320 minutes (three days); Teams `chat`, `channel`, `conversationMember`, `team` also 4,320 minutes; "Existing applications and new applications should not exceed the supported value. In the future, any requests to create or renew a subscription beyond the maximum value will fail" (include dated 11/07/2024) — [Change notifications overview – Subscription lifetime](https://learn.microsoft.com/en-us/graph/change-notifications-overview#subscription-lifetime); **contradicted by** the Teams-specific overview (page dated 03/16/2026): "The maximum time a subscription can last is 60 minutes; however, subscriptions can be renewed until the caller has permission to access the resource" — [Change notifications for Microsoft Teams resources](https://learn.microsoft.com/en-us/graph/teams-change-notification-in-microsoft-teams-overview)
- Subscription-creation permission table rows for `chatMessage`: `/teams/{id}/channels/{id}/messages` → Delegated `ChannelMessage.Read.All`; Application `ChannelMessage.Read.Group`*, `ChannelMessage.Read.All`; `/teams/getAllMessages` → Application `ChannelMessage.Read.All`; `/chats/{id}/messages` → Delegated `Chat.Read`, `Chat.ReadWrite`; Application `Chat.Read.All`; `/chats/getAllMessages` → Application `Chat.Read.All`; `/users/{id}/chats/getAllMessages` → Delegated `Chat.Read`, `Chat.ReadWrite`; Application `Chat.Read.All`, `Chat.ReadWrite.All`; `chat` (`/chats/{id}`) application includes RSC `ChatSettings.Read.Chat`*, `Chat.Manage.Chat`*; `conversationMember` (`/chats/{id}/members`) application includes `ChatMember.Read.Chat`* — [Create subscription](https://learn.microsoft.com/en-us/graph/api/subscription-post-subscriptions?view=graph-rest-1.0)
- Lifecycle notifications (page dated 12/20/2024): three kinds — `reauthorizationRequired` (all resources), `subscriptionRemoved` (supported for Outlook message/event/contact and **Teams chatMessage**), `missed` (Outlook only). `lifecycleNotificationUrl` "can be the same as the notificationUrl"; it cannot be added to an existing subscription (delete and re-create); respond `202 Accepted`, validate, then either `POST /subscriptions/{id}/reauthorize` or `PATCH /subscriptions/{id}` with a new `expirationDateTime` ("To reauthorize and renew a subscription in the same request, use a single PATCH"; "Don't issue a reauthorize request and an update request for the same subscription within a 10-minute window"); after a pause "Any notifications about resource changes that happen when the change notification delivery pauses ... are lost. In such cases, the app should separately fetch those changes, for example using the delta query" — [Reduce missing subscriptions and change notifications](https://learn.microsoft.com/en-us/graph/change-notifications-lifecycle-events)
- Rich notifications (`includeResourceData: true`) require `encryptionCertificate` (Base64 X.509 **public key only**; self-signed OK; RSA 2,048–4,096 bits; Key Vault recommended) and `encryptionCertificateId`; payload carries `encryptedContent.data`, `dataKey`, `encryptionCertificateId`, `encryptionCertificateThumbprint` and a `validationTokens` JWT array that must be validated (signing keys from `https://login.microsoftonline.com/common/.well-known/openid-configuration`; `azp` must be `0bf30f3b-4a52-48df-9a82-234910c4a086`); a `null` `validationTokens` means Graph could not encrypt due to app misconfiguration; if the service principal has `appRoleAssignmentRequired = true`, assign an app role to the *Microsoft Graph Change Tracking* service principal (appId `0bf30f3b-4a52-48df-9a82-234910c4a086`) — [Set up change notifications that include resource data](https://learn.microsoft.com/en-us/graph/change-notifications-with-resource-data)
- Notifications **without** resource data "don't require an encryption certificate"; the payload's `resource` / `@odata.id` (e.g. `teams('…')/channels('…')/messages('…')`) is used for a follow-up GET, and "GET calls always return the current state of the message" — [Get change notifications for messages](https://learn.microsoft.com/en-us/graph/teams-changenotifications-chatmessage#notifications-without-resource-data)
- Delivery rules (page dated 01/15/2025): a notification counts as delivered when the endpoint returns 2xx **within 3 seconds**; otherwise Graph retries for up to 4 hours with a 10-second timeout on retries; recommended pattern is validate, enqueue, return `202 Accepted`; return 5xx if not queued; an endpoint is marked "drop" when more than 15% of responses exceed the 10-second allowance in a 10-minute window (dropped notifications are unrecoverable); `clientState` "is required" and must be validated on every notification; notificationUrl validation handshake must echo the `validationToken` as plain text; if the app's access token expires, notifications are still retried for 4 hours — [Change notifications delivered via webhooks](https://learn.microsoft.com/en-us/graph/change-notifications-delivery-webhooks)
- Latency: `chatMessage` average "Less than 10 seconds", maximum 1 minute (include dated 11/07/2024) — [Change notifications overview – Latency](https://learn.microsoft.com/en-us/graph/change-notifications-overview#latency)
- Subscription-service throttling: POST/PUT/DELETE/PATCH 500 requests per 20 s per app per tenant (2,000 across all tenants); `POST /reauthorize` 1,000 per 20 s per tenant; GET subscription by id 500 per 20 s; GET subscription list 25 per 20 s per tenant — [Throttling limits – Subscription service limits](https://learn.microsoft.com/en-us/graph/throttling-limits#subscription-service-limits)
- RSC scope caveat: "When an agent or app is installed in a team, its channel-related RSC permissions automatically extend to all of the team's channels except private and shared channels. Channel-related RSC permissions only extend to private and shared channels in which a user has explicitly added the agent or app" (page dated 10/18/2026) — [Resource-specific consent](https://learn.microsoft.com/en-us/microsoftteams/platform/graph-api/rsc/resource-specific-consent)
- Field report (March 2026, unverified): a bot with RSC receives every new message in standard channels but in **shared channels** only receives events when explicitly @mentioned; poster suggests message change notifications for `/channels/{id}/messages` are not supported for shared channels with RSC and recommends on-demand reads/delta polling as fallback (search snippet) — [Microsoft Tech Community discussion](https://techcommunity.microsoft.com/discussions/teamsdeveloper/bot-not-receiving-message-events-in-shared-channels-rsc/4506262)

### Inferences
- Safest subscription design for a small tenant: one subscription per project channel/chat, `changeType: "created,updated,deleted"`, `expirationDateTime` ≤ 60 minutes **or** up to 3 days with a `lifecycleNotificationUrl`; renew by `PATCH` on a schedule and on `reauthorizationRequired`; recreate on `subscriptionRemoved`; run a nightly reconciliation GET to catch lost notifications. Given the 60-minute vs 3-day contradiction, request ≤ 3 days but tolerate a server-side clamp.
- Skip resource data (no certificate management) and GET the message after each notification; the 1 rps per channel GET limit (Q4) is ample for a 20–50 person company.
- Use `/teams/{id}/channels/{id}/messages` (RSC-capable on v1.0) for project channels; for *group chats* note the RSC `ChatMessage.Read.Chat` subscription is documented as beta-only — if chats are used, plan to use beta or the app-installed route `/appCatalogs/teamsApps/{id}/installedToChats/getAllMessages` with `Chat.Read.WhereInstalled`.

### Gaps
- Whether `ChatMessage.Read.Chat` RSC now works for v1.0 chat-message subscriptions (the beta-only note is dated 11/07/2024) could not be re-verified.
- The exact per-app/per-tenant cap on the number of active subscriptions was not found in the pages read.

## Q3. "Protected APIs" approval, resource-specific consent (RSC), and metered pricing status (2025–2026)

### Takeaway
Tenant-wide application permissions such as `ChannelMessage.Read.All` / `Chat.Read.All` are "protected" and need a Microsoft request form on top of admin consent, whereas RSC permissions (`ChannelMessage.Read.Group`, `ChatMessage.Read.Chat`) are granted by the team/chat owner at app install with no form; and **as of 25 August 2025 the Teams message APIs and notifications are no longer metered**, so the former model A/B per-message billing no longer applies.

### Cited Findings
- "Starting August 25, 2025, the Teams APIs are no longer metered, and no billing configuration is required to use these APIs. If your application is configured for billing, no action is required. The SharePoint and OneDrive ... assignSensitivityLabel API remains metered" (page dated 08/06/2025); the same page says "Some metered APIs and services in Microsoft Graph are protected and require additional validation beyond permissions and admin consent. Before you can use these protected APIs, you must submit a request" — [Metered APIs and services in Microsoft Graph](https://learn.microsoft.com/en-us/graph/metered-api-list)
- Historical pricing (superseded): the payment-models page listed change-notification and message resources at $0.00075 USD per message, model A with seeded capacity of 800 messages × licensed seats with DLP per month per app, model B with no seeded capacity (search snippet of a page that could not be opened) — [Payment models and licensing requirements for Microsoft Teams APIs](https://learn.microsoft.com/en-gb/graph/teams-licenses); a Microsoft Q&A answer citing Message Center item MC1122144 says selecting model A or B is no longer required (search snippet) — [Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/5828700/payment-for-teams-export-apis-getallmessages-and-g)
- Protected status: Microsoft Q&A/vendor reports say `ChannelMessage.Read.All` application access requires completing Microsoft's protected-API request form; without approval the error is "Invoked API requires Protected API access in application-only context when not using Resource Specific Consent" or a bare 403 `UnknownError`; a forum post gives the form as aka.ms/teamsgraph/requestaccess and a vendor note says the form asks "Why does your application need read access to all messages in the tenant?" (search snippets, not verified against the official page) — [Microsoft Q&A: ChannelMessage.Read.All returns 403](https://learn.microsoft.com/en-us/answers/questions/6049168/channelmessage-read-all-application-permission-ret); [ActiveNav support note](https://support.activenav.com/requesting-extra-approval-for-protected-apis-from-microsoft)
- RSC model (page dated 10/18/2026): RSC permissions "extend only to the teams, chats, meetings, and user personal scopes where they are installed"; "RSC permissions are not declared or displayed in the Entra admin center"; app-only RSC: Microsoft Graph and Teams SDK, app manifest ≥ v1.6, consent by "Team: A team owner or member; Chat: A chat member; Meeting: organizer or presenter", tenant-level controls "Microsoft Graph-based controls for chats and meetings; Microsoft Entra admin center-based controls for Teams"; delegated RSC needs manifest ≥ v1.12; "Installing an agent or app requires consenting to all of its RSC permissions requests: users can't grant or deny permissions individually" — [Resource-specific consent](https://learn.microsoft.com/en-us/microsoftteams/platform/graph-api/rsc/resource-specific-consent)
- Same page lists team RSC permissions incl. `ChannelMessage.Read.Group` ("Read and receive all of this team's channel messages", app-only), `ChannelMessage.Send.Group` ("Send messages to this team's channels", app-only), `Channel.Create.Group`, `Channel.Delete.Group`, `ChannelSettings.Read.Group`/`ReadWrite.Group`, `TeamMember.Read.Group`, `ChannelMember.Read.Group`/`ReadWrite.Group`, `TeamSettings.Read.Group`/`ReadWrite.Group`, `TeamsTab.*.Group`, `TeamsAppInstallation.Read.Group`, `File.Read.Group`, `TeamsActivity.Send.Group`; chat RSC incl. `ChatMessage.Read.Chat` ("Read and receive all of this chat's messages"), `ChatMessageReadReceipt.Read.Chat` ("Read the ID of the last seen message in this chat"), `ChatMember.Read.Chat`, `Chat.Manage.Chat`, `ChatSettings.Read.Chat`/`ReadWrite.Chat`, `TeamsAppInstallation.Read.Chat`, `TeamsActivity.Send.Chat`; "basic" always-consented permissions `TeamsActivity.Send.Group/Chat/User` — [Resource-specific consent](https://learn.microsoft.com/en-us/microsoftteams/platform/graph-api/rsc/resource-specific-consent)
- Declaring RSC (page dated 10/26/2026): in manifest v1.12+ add `webApplicationInfo.id` (the Entra application client ID) and `authorization.permissions.resourceSpecific: [{ "name": "ChannelMessage.Read.Group", "type": "Application" }, …]`; "Teams supports a maximum of 16 RSC permissions declarations per agent or app"; can also be set in Developer Portal → Configure → Permissions — [Declare RSC permission requirements](https://learn.microsoft.com/en-us/microsoftteams/platform/graph-api/rsc/declare-resource-specific-consent-requirements)
- Receive-all doc (page dated 10/09/2026): "By default, in group chats and channels, the only chat messages that an agent receives or can access through Graph APIs are the messages in which it's @mentioned"; declaring `ChannelMessage.Read.Group` and/or `ChatMessage.Read.Chat` lifts this; "The team or chat owner must consent to the requested RSC permissions during installation"; "Teams doesn't deliver messages authored by other agents or bots, including the Workflows (Power Automate) bot, to your agent ... This limitation applies to message delivery to the agent, not to reading messages through Microsoft Graph APIs"; example manifest uses `"resource": "https://RscBasedStoreApp"` — [Configure an agent to receive all messages in group chats and channels](https://learn.microsoft.com/en-us/microsoftteams/platform/agents-in-teams/enable-receive-all-chat-messages)
- The Graph permission reference marks `ChannelMessage.Read.All` as Application + Delegated and `Chat.Read.All` as Application-only — [Microsoft Graph permissions reference](https://learn.microsoft.com/en-us/graph/permissions-reference)

### Inferences
- For a 20–50 user Japanese company with no IT department, RSC is the right default: install the custom app into each project team (or group chat) and avoid tenant-wide `*.All` message permissions entirely; this removes the Microsoft approval form from the critical path and keeps data access bounded to project conversations.
- Metering removal means cost planning for notifications/reads is no longer needed, but the "protected" gate still exists for tenant-wide `ChannelMessage.Read.All` / `Chat.Read.All` / `getAllMessages` export APIs.

### Gaps
- The official protected-APIs page (`/graph/teams-protected-apis`) could not be retrieved; the exact current list of protected permissions, form URL, SLA and eligibility (e.g. whether a single-tenant line-of-business app qualifies) are unverified.
- The RSC page says app-only RSC can be granted by "a team owner or member" in one table but "only administrators or resource owners can grant app-only RSC permissions" in prose; which applies in a given tenant depends on the Teams admin "consent to app permissions" settings, which were not retrievable.

## Q4. Throttling limits for Teams Graph calls (2025–2026)

### Takeaway
Per-app-per-tenant limits are the ones a single-tenant app hits: 20 rps for listing channel or chat messages, 1 rps per individual channel/chat, 50 rps for posting channel messages, and 10 rps for creating channels; limits are evaluated over bursts with a sustained ceiling of ≈83% of the listed value, so steady-state traffic must stay below that and use exponential backoff on 429.

### Cited Findings
- Teams throttling dimensions: per app (all tenants), per app per tenant ("The most commonly reached limit"), per resource, per user; "A sustained limit of approximately 83 percent of the listed value is also evaluated over a longer window, so a workload that runs continuously at the listed rate can still be throttled" (page dated 01/14/2025 with Teams include) — [Microsoft Graph service-specific throttling limits – Microsoft Teams](https://learn.microsoft.com/en-us/graph/throttling-limits#microsoft-teams-service-limits)
- Channel messages: `GET /teams/{team-id}/channels/{channel-id}/messages` 200 rps per app / **20 rps per app per tenant** / **1 rps per channel**; `POST .../messages` 500 / 50 / 1 rps per channel / 1 rps per user; `POST .../messages/{id}/replies` same as POST — [same page](https://learn.microsoft.com/en-us/graph/throttling-limits#microsoft-teams-service-limits)
- Chat messages: `GET /chats/{chat-id}/messages` 200 / 20 / 1 rps per chat; `POST /chats/{chat-id}/messages` 200 / 20 / 1 rps per chat / 1 rps per user; `GET /chats/{chat-id}` 2000 / 200 / 1 rps per chat / 5 rps per user; `GET /chats` 200 / 20 / – / 1 rps per user; `POST /chats` 200 / 20 — [same page](https://learn.microsoft.com/en-us/graph/throttling-limits#microsoft-teams-service-limits)
- Channels: `GET /teams/{id}/channels` 1200 / 60 / 4 rps per team; `POST /teams/{id}/channels` 100 / **10** / 4 rps per team; `GET .../channels/{id}/members` 1200 / 60 / 1 rps per channel — [same page](https://learn.microsoft.com/en-us/graph/throttling-limits#microsoft-teams-service-limits)
- Members: `POST /teams/{id}/members` 300 / 30 / **4 requests per minute per team**; `POST /chats/{id}/members` 300 / 30 / 4 requests per minute per chat — [same page](https://learn.microsoft.com/en-us/graph/throttling-limits#microsoft-teams-service-limits)
- Bulk retrieval (`channels/getAllMessages`, `users/{id}/chats/getAllMessages`, `getAllRetainedMessages`): 1000 rps per app / 200 rps per app per tenant — [same page](https://learn.microsoft.com/en-us/graph/throttling-limits#microsoft-teams-service-limits)
- Activity feed: `POST /teams/{id}/sendActivityNotification` 50 / 5 / 4 rps per team; `/chats/{id}/sendActivityNotification` 50 / 5 / 1 rps per chat; `/users/{id}/teamwork/sendActivityNotification` 50 / 5 — [same page](https://learn.microsoft.com/en-us/graph/throttling-limits#microsoft-teams-service-limits)

- Subscription service limits: see Q2 (500 writes per 20 s per app per tenant) — [Throttling limits – Subscription service limits](https://learn.microsoft.com/en-us/graph/throttling-limits#subscription-service-limits)
- Field reports of 429s below documented limits exist (e.g. a Q&A citing "3000 requests per app per tenant per 30 seconds" and another citing "60 requests per minute per app per tenant" for message APIs); these figures are not in the official table (search snippets) — [Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/5565131/has-anyone-encountered-similar-inconsistent-rate-l)

- Workflows webhook (replacement for Incoming Webhook): "The message size limit is 28 KB"; "If more than four requests are made in a second, the client connection is throttled" (page dated 10/26/2026) — [Create Incoming Webhooks](https://learn.microsoft.com/en-us/microsoftteams/platform/webhooks-and-connectors/how-to/add-incoming-webhook)

### Inferences
- A company with, say, 100 active project channels doing a nightly sweep of 2 GETs per channel (root + replies) is ≈200 requests, trivially within limits if serialized at ≤1 request/second per channel and ≤~15 rps overall.
- Design the notification receiver to enqueue and return 202 immediately (3-second rule) and do Graph reads from a worker with a token-bucket at ~15 rps.

## Q5. Determining whether the last message came from a customer/guest or staff, and how long it has gone unanswered (requirement b)

### Takeaway
Use `chatMessage.from`: `from.application` ≠ null means a bot/connector/workflow; `from.user.userIdentityType` plus `from.user.tenantId` distinguishes in-tenant staff (`aadUser` in the home tenant) from guests/external users (`anonymousGuest`, `federatedUser`, `personalMicrosoftAccountUser`, `emailUser`, or `aadUser` with a foreign `tenantId`); cross-check against channel/chat membership roles (`guest`) and compute age from `createdDateTime` of the newest message across root posts and replies.

### Cited Findings
- `chatMessageFromIdentitySet`: `application` "If present, represents the application (for instance, bot) that sent the message"; `user` is a `teamworkUserIdentity` (page dated 07/22/2024) — [chatMessageFromIdentitySet](https://learn.microsoft.com/en-us/graph/api/resources/chatmessagefromidentityset?view=graph-rest-1.0)
- `teamworkUserIdentity.userIdentityType` values: `aadUser`, `onPremiseAadUser`, `anonymousGuest`, `federatedUser`, `personalMicrosoftAccountUser`, `skypeUser`, `phoneUser`, `unknownFutureValue`, `emailUser`; `tenantId` "Identifier of tenant, which user is part of. Optional." (page dated 07/22/2024) — [teamworkUserIdentity](https://learn.microsoft.com/en-us/graph/api/resources/teamworkuseridentity?view=graph-rest-1.0)
- Application sender sub-types usable in `$filter` on export APIs: `aadApplication`, `bot`, `tenantBot`, `office365Connector`, `outgoingWebhook` — [chats: getAllMessages](https://learn.microsoft.com/en-us/graph/api/chats-getallmessages?view=graph-rest-1.0)
- Membership roles: when creating a chat, "Each member must be assigned a role of `owner` or `guest`. In-tenant guest users must be assigned the `guest` role. Out-of-tenant external users must be assigned with `owner` role" (page dated 05/29/2024) — [Create chat](https://learn.microsoft.com/en-us/graph/api/chat-post?view=graph-rest-1.0)
- `GET /teams/{team-id}/channels/{channel-id}/allMembers` "supports all channel types, including shared channels" and returns direct and indirect members with `roles` and `tenantId`, with `@microsoft.graph.originalSourceMembershipUrl` identifying indirect (shared-team) members — [List allMembers](https://learn.microsoft.com/en-us/graph/api/channel-list-allmembers?view=graph-rest-1.0)
- `channel.membershipType` ∈ `standard`, `private`, `shared` (`shared` requires `Prefer: include-unknown-enum-members`); `channel.tenantId` is the hosting tenant (page dated 10/02/2024) — [channel resource type](https://learn.microsoft.com/en-us/graph/api/resources/channel?view=graph-rest-1.0)
- `messageType` `systemEventMessage` marks system events (member added etc.) and `eventDetail` describes them; `lastModifiedDateTime` changes on reactions; `replyToId` identifies thread parent in channels only — [chatMessage resource type](https://learn.microsoft.com/en-us/graph/api/resources/chatmessage?view=graph-rest-1.0)
- Change-notification payloads carry `changeType` (`created`/`updated`/`deleted`) and `tenantId`, and the decrypted/fetched payload is a full `chatMessage` including `from.user.userIdentityType` — [Get change notifications for messages](https://learn.microsoft.com/en-us/graph/teams-changenotifications-chatmessage#notification-payloads)
- Read receipts in chats: RSC `ChatMessageReadReceipt.Read.Chat` "Read the ID of the last seen message in this chat" — [Resource-specific consent](https://learn.microsoft.com/en-us/microsoftteams/platform/graph-api/rsc/resource-specific-consent)

### Inferences
- Classification rule for an "unanswered customer message" detector: (1) ignore `messageType != message`, `deletedDateTime != null`, and `from.application != null` (bots, Workflows, connectors); (2) treat sender as **customer/guest** if `from.user.userIdentityType ∈ {anonymousGuest, federatedUser, personalMicrosoftAccountUser, emailUser, phoneUser, skypeUser}` or `tenantId != homeTenantId`, or if the user's membership role in that channel/chat is `guest`; otherwise **staff**; (3) per thread, find the newest message by `createdDateTime` across root + replies; if it is a customer message, age = now − `createdDateTime`; thresholds (green/yellow/red) are a business choice, e.g. <4h / 4–24h / >24h.
- Maintain a cached staff directory (Entra user IDs of employees) so that in-tenant `aadUser` guests (Entra B2B guests, `userType = Guest`) are still classified as customers; `userIdentityType` alone may show `aadUser` for B2B guests signed into your tenant, so membership role or directory lookup is the more reliable discriminator.

### Gaps
- No Microsoft page read states explicitly which `userIdentityType` value a B2B (email OTP) guest produces in `chatMessage.from`; verify empirically in the tenant.

## Q8. Power Automate / Workflows: triggers on new channel messages, posting cards, and licensing limits on Business Standard/Premium

## Q9. Creating per-project channels or chats automatically (requirement d) and posting into them

### Takeaway
Create channels app-only with `POST /teams/{team-id}/channels` using RSC `Channel.Create.Group` (or `Channel.Create`), create group chats with `POST /chats` using `Chat.Create`; but **Graph application permissions cannot post ordinary messages** (`Teamwork.Migrate.All` is for migration only), so alerts must be posted by a bot, by a delegated user token (`ChannelMessage.Send` / `ChatMessage.Send`), or via a Workflows webhook.

### Cited Findings
- `POST /teams/{team-id}/channels`: `displayName` max 50 characters; private channels max 200 members; shared channel creation returns `202 Accepted` + `teamsAsyncOperation` and "You can create shared channels with only one owner initially"; SharePoint site for private/shared channels may take time to provision (page dated 09/18/2024); permissions: Delegated least `Channel.Create` (higher `Directory.ReadWrite.All`, `Group.ReadWrite.All`); Application least `Channel.Create.Group` (RSC) (higher `Channel.Create`, `Directory.ReadWrite.All`, `Group.ReadWrite.All`, `Teamwork.Migrate.All`); "Group.ReadWrite.All and Directory.ReadWrite.All permissions are supported only for backward compatibility" — [Create channel](https://learn.microsoft.com/en-us/graph/api/channel-post?view=graph-rest-1.0)

- Add channel member: `POST /teams/{team-id}/channels/{channel-id}/members` is "Only supported for channels with a membershipType of `private` or `shared`" — [channel resource type](https://learn.microsoft.com/en-us/graph/api/resources/channel?view=graph-rest-1.0)
- Posting messages: `POST /teams/{team-id}/channels/{channel-id}/messages`, `.../messages/{message-id}/replies`, `POST /chats/{chat-id}/messages`; permissions (channel): Delegated least `ChannelMessage.Send` (higher `Group.ReadWrite.All`), Application least `Teamwork.Migrate.All` ("Application permissions are only supported for migration"); (chat): Delegated least `ChatMessage.Send` (higher `Chat.ReadWrite`, `Group.ReadWrite.All`), Application `Teamwork.Migrate.All`; the Teams client has HTML restrictions (`<div>`/inline styles may not render) — [Send chatMessage in a channel or a chat](https://learn.microsoft.com/en-us/graph/api/chatmessage-post?view=graph-rest-1.0)

- Throttling for creation: `POST /teams/{id}/channels` 10 rps per app per tenant and 4 rps per team; `POST /chats` 20 rps per app per tenant; adding members 4 requests/minute per team or chat — [Throttling limits](https://learn.microsoft.com/en-us/graph/throttling-limits#microsoft-teams-service-limits)

## Q10. External/guest access: can customers (施主) be invited as guests or into shared channels (Teams Connect)? Pros/cons vs keeping customers on LINE

### Takeaway
Customers without a Microsoft 365 work account can join as **B2B collaboration guests** (invited by email; sign-in via email one-time passcode, on by default) in a team or group chat; **shared channels** (Teams Connect / B2B direct connect) require the customer to have their own Microsoft Entra organization and a mutual cross-tenant trust, so they suit partner firms, not individual homeowners. Guest data lands in your tenant (so your retention/eDiscovery apply), but the customer must install/use Teams, which is the main UX trade-off against LINE.

### Cited Findings
- Email one-time passcode (page dated 03/27/2026): "The email one-time passcode feature is now turned on by default for all new tenants and for any existing tenants where you haven't explicitly turned it off"; used when a B2B guest "can't be authenticated through other means, such as Microsoft Entra ID, Microsoft account (MSA), or social identity providers"; "Email one-time passcode guest users can sign in to Microsoft Teams directly from the common endpoint"; passcodes valid 30 minutes; "User sessions expire after 24 hours"; if the feature is disabled "the user is prompted to create a Microsoft account" — [Email one-time passcode authentication for B2B guest users](https://learn.microsoft.com/en-us/entra/external-id/one-time-passcode)
- B2B direct connect (page dated 04/24/2026): "lets you set up a mutual trust relationship with another Microsoft Entra organization ... This feature currently works with Microsoft Teams shared channels"; "Both the resource organization and the external organization need to mutually enable B2B direct connect in their cross-tenant access settings"; "Initially, Microsoft Entra ID blocks all inbound and outbound B2B direct connect capabilities by default"; direct-connect users "don't have a presence in your Microsoft Entra organization, so these users are managed in the Teams client by the shared channel owner"; "With B2B collaboration, you can invite the guest user to a team ... Guest users can't see or participate in any shared channels in the team"; reporting "is available in both the Azure portal and the Microsoft Teams admin center" — [B2B direct connect overview](https://learn.microsoft.com/en-us/entra/external-id/b2b-direct-connect-overview)
- Shared vs private channels for apps (Teams platform): shared channels "Allow seamless communication with internal or external members, without changing the user's context"; external users can participate in private channels as "B2B collaboration users" and in shared channels as cross-tenant users; apps should "validate user roles and tenant IDs before granting permissions"; private and shared channels have their own SharePoint sites; the activity feed API "doesn't support cross-tenant notifications for apps in a shared channel" — [Apps for shared and private channels](https://learn.microsoft.com/en-us/microsoftteams/platform/build-apps-for-shared-private-channels)
- Search summaries of the Teams admin shared-channels guidance: external participants "access shared resources in your organization by using their own Microsoft Entra ID or Microsoft 365 identity", don't need a guest account or a license from you, "guest access in Teams must be enabled to invite them", cross-tenant access must be configured by an Entra admin for each external org, and shared channels "don't replace guest access" (search snippets) — [Shared channels in Microsoft Teams](https://learn.microsoft.com/en-us/microsoftteams/shared-channels); [Plan external collaboration](https://learn.microsoft.com/en-us/microsoft-365/solutions/plan-external-collaboration)

### Inferences
- For homeowners (個人の施主): B2B guest invitation to a per-project **private channel** or a **group chat** is the viable Teams route (email OTP, no Microsoft account needed); shared channels are not usable unless the customer belongs to an Entra organization (e.g. a corporate client or a design office).

## Q11. Identity, security and compliance: Entra app registration, application vs delegated permissions, admin consent, audit, Japan data residency, retention/eDiscovery implications

### Takeaway
Run the integration as a single-tenant Entra app with **application (app-role) permissions limited to RSC scopes plus `Chat.Create`/`Channel.Create.Group`/`TeamsAppInstallation.ReadWriteSelfForTeam.All`**; Graph application permissions can only be consented by a Privileged Role Administrator (or Global Admin), while RSC grants happen in Teams at install time and are invisible in the Entra admin center. Teams chat/channel data for a Japan-registered tenant is stored at rest in Japan without add-ons (Multi-Geo is not available to small-business SKUs), and messages posted by bots/flows become ordinary Teams messages subject to Purview retention/eDiscovery, whereas activity-feed notifications may not be.

### Cited Findings
- Admin consent roles (page dated 03/25/2025): "Privileged Role Administrator, for granting consent for apps requesting any permission, for any API"; "Cloud Application Administrator, AI Administrator, or Application Administrator, for granting consent for apps requesting any permission for any API, *except* Microsoft Graph app roles (application permissions)"; application permissions "are also known as app roles" and let the app run "as a background service or daemon without a signed-in user" — [Grant tenant-wide admin consent to an application](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/grant-admin-consent)
- Proactive-install permissions need a Microsoft Entra admin to "explicitly grant permissions to an application. After the application is granted permissions, all members of the Microsoft Entra tenant get the granted permissions" — [Proactively install your bot](https://learn.microsoft.com/en-us/microsoftteams/platform/graph-api/proactive-bots-and-messages/graph-proactive-bots-and-messages)
- RSC permissions "are not declared or displayed in the Entra admin center. If you want to know the RSC permissions associated with an app, see the app installation or app information dialog within the Teams client"; tenant controls differ for chats/meetings (Graph-based) vs teams (Entra admin center-based) — [Resource-specific consent](https://learn.microsoft.com/en-us/microsoftteams/platform/graph-api/rsc/resource-specific-consent)
- Change-notification security: `clientState` secret validation; JWT `validationTokens` validation for rich notifications; private key for decrypting resource data should be secured (Key Vault) — [Set up change notifications that include resource data](https://learn.microsoft.com/en-us/graph/change-notifications-with-resource-data); [Change notifications delivered via webhooks](https://learn.microsoft.com/en-us/graph/change-notifications-delivery-webhooks)
- Japan data residency (page dated 05/08/2025): Teams "Chat/channel messages and team structure ... are stored in an Azure powered chat service. The data is also stored in a hidden folder in the user and group mailboxes to enable information protection features"; media stored "in an Azure based Media Service deployed to the same locations as the chat service"; default commitment applies when the tenant's sign-up country is in a Local Region Geography; Advanced Data Residency add-on gives further commitments — [Data residency for Microsoft Teams](https://learn.microsoft.com/en-us/microsoft-365/enterprise/m365-dr-service-teams)
- Japan is a "Local Region Geography" and Microsoft 365 datacenters for Japan are in Osaka and Tokyo (page dated 2026) — [Data residency overview](https://learn.microsoft.com/en-us/microsoft-365/enterprise/m365-dr-overview); Japan is also listed among countries with Advanced Data Residency (page dated 04/01/2026) — [Where your Microsoft 365 customer data is stored](https://learn.microsoft.com/en-us/microsoft-365/enterprise/o365-data-locations)
- Multi-Geo add-on is available only to Microsoft 365 F1/F3/E3/E5, Office 365 F3/E1/E3/E5, Teams Enterprise/EEA/Essentials etc.; "**Small Business products do not currently qualify for Multi-Geo**" — [Microsoft 365 Multi-Geo](https://learn.microsoft.com/en-us/microsoft-365/enterprise/microsoft-365-multi-geo)
- Compliance caveat: `TeamsActivity.Send` notifications "may not be discoverable or be held or governed by compliance policies" — [permissions reference](https://learn.microsoft.com/en-us/graph/permissions-reference)
- eDiscovery: Microsoft's current guidance is the Purview eDiscovery (Premium) workflow for Teams content (chats, channel posts, attachments); the classic eDiscovery experiences were retired on 31 August 2025 (search snippets) — [eDiscovery (Premium) workflow for content in Microsoft Teams](https://learn.microsoft.com/en-us/purview/ediscovery-teams-workflow)
- B2B direct connect audit reporting exists in the Azure portal and Teams admin center — [B2B direct connect overview](https://learn.microsoft.com/en-us/entra/external-id/b2b-direct-connect-overview)
- Graph export of messages: `getAllRetainedMessages` endpoints exist for compliance export (throttling table) — [Throttling limits](https://learn.microsoft.com/en-us/graph/throttling-limits#microsoft-teams-service-limits)

### Inferences
- Least-privilege permission set for the app registration (application type): none of the `*.All` message permissions; RSC `ChannelMessage.Read.Group`, `ChatMessage.Read.Chat`, `ChannelMember.Read.Group`, `ChatMember.Read.Chat`, `Channel.Create.Group`, `TeamsActivity.Send.Group/Chat`; Graph app roles `Chat.Create` and `TeamsAppInstallation.ReadWriteSelfForTeam.All` (admin consent once by a Global/Privileged Role Admin); use certificate credentials or managed identity, store the webhook `clientState` and any decryption key in Key Vault, and keep `appRoleAssignmentRequired` handling in mind for rich notifications.

- Business Premium tenants registered in Japan get Teams data at rest in Japan by default; no Multi-Geo/ADR purchase is possible or needed for the stated scale.

### Inferences
- Reference architecture for the AI coding agent (synthesized from the cited Microsoft docs):
  1. **Teams app** (manifest v1.17+, `webApplicationInfo.id` = Entra app, RSC `ChannelMessage.Read.Group`, `ChatMessage.Read.Chat`, `ChannelMember.Read.Group`, `Channel.Create.Group`, `TeamsActivity.Send.Group`) wrapping an Azure Bot built with Teams SDK; published to the org catalog and installed into the "案件" team(s).
  2. **Ingestion**: two redundant paths — (a) bot `message` activities (real-time, no polling), (b) Graph change-notification subscriptions per project channel/chat (`created,updated,deleted`, no resource data, ≤3-day expiry with `lifecycleNotificationUrl`), plus a nightly reconciliation GET (`$top=50` root + replies) to repair gaps.
  3. **State**: per thread store last message `createdDateTime`, sender class (customer/staff/bot from Q5 rules), last staff reply time; compute SLA colour on a timer (working hours in `Asia/Tokyo`).
  4. **Alerts**: bot proactive Adaptive Card (`Action.Execute` buttons "対応する / 担当割当 / 案件を開く") into the project channel thread (`app.ReplyAsync`) or a central alert channel; daily digest at a fixed JST time via the same bot (or a Workflows webhook URL as a lower-privilege fallback).
  5. **Provisioning**: app-only `POST /teams/{id}/channels` (+ `installedApps` upgrade for private/shared channels) and `POST /chats` when a case is created; subscriptions created immediately after.
  6. **Ops**: exponential backoff on 429 (Graph and bot), 202-within-3-seconds webhook handler, Key Vault for secrets, audit via Entra sign-in logs for the service principal.
