## Key Question 1 — Spec-driven development: what sections do Spec Kit / Kiro / PRD→plan→tasks workflows require, and what evidence exists on outcomes?

### Takeaway
All major SDD toolkits converge on the same artifact chain — constitution/steering (standing rules) → spec (WHAT/WHY: prioritized user stories with Given/When/Then or EARS acceptance criteria, numbered testable requirements, key entities, measurable technology-agnostic success criteria, assumptions, bounded open questions) → plan (technical context, data model, contracts, research) → dependency-ordered tasks with file paths → implement → converge/verify. Rigorous outcome evidence is thin: the only quantified comparison found (single-developer case study) reports fewer missed bugs and fewer failed test runs but ~3x token cost; practitioner reports (Böckeler/Thoughtworks, Japanese speakers) warn that generated specs are verbose and that specs alone do not stop mediocre code.

### Cited Findings

**GitHub Spec Kit (github/spec-kit) — structure and phrasing (all retrieved 2026-11-07 from the `main` branch; README references "Spec Kit 1.0" and events dated Oct 2026)**
- Spec Kit's one-line definition: "Define what to build and why, then turn the specification into a plan, tasks, and working code." Command order: `/speckit-constitution` → `/speckit-specify` → `/speckit-plan` → `/speckit-tasks` → `/speckit-implement` → `/speckit-converge`; "Repeat implement and converge until convergence reports `Converged`." The constitution is created once per project; the remaining steps repeat per feature; commands are run one at a time, reviewing each result before continuing. — [Spec Kit README](https://raw.githubusercontent.com/github/spec-kit/main/README.md)
- Core philosophy ("the power inversion"): "Specifications don't serve code—code serves specifications." Specs must be "precise, complete, and unambiguous enough to generate working systems." Spec guidance: "Focus on WHAT users need and WHY"; avoid "HOW to implement (no tech stack, APIs, code structure)"; use "[NEEDS CLARIFICATION: specific question]" for unknowns; checklist: no clarification markers remain, requirements are testable, success criteria are measurable; avoid speculative features. — [spec-driven.md](https://raw.githubusercontent.com/github/spec-kit/main/spec-driven.md)
- Plan artifacts: `plan.md`, `research.md`, `data-model.md`, `contracts/`, `quickstart.md`; "Phase -1 gates" (Simplicity, Anti-Abstraction, Integration-First) with checks such as "No future-proofing?", "Using framework directly?", "Contracts defined?", "Contract tests written?"; keep the plan "high-level and readable", push code samples into `implementation-details/`. — [spec-driven.md](https://raw.githubusercontent.com/github/spec-kit/main/spec-driven.md)
- Constitution articles in the reference spec: Article I Library-First ("Every feature in Specify MUST begin its existence as a standalone library"), II CLI Interface (text in/out, JSON), III Test-First ("No implementation code shall be written before:" tests are written, approved, and confirmed to fail), VII Simplicity ("Maximum 3 projects for initial implementation"), VIII Anti-Abstraction ("Use framework features directly rather than wrapping them"), IX Integration-First ("Prefer real databases over mocks"; "Contract tests mandatory before implementation"). — [spec-driven.md](https://raw.githubusercontent.com/github/spec-kit/main/spec-driven.md)
- Development phases named by Spec Kit: "0-to-1 (Greenfield)", "Creative Exploration" (parallel implementations to compare stacks/architectures/UX), "Iterative Enhancement (Brownfield)". Core principles: intent-driven ("specifications define the 'what' before the 'how'"), "Rich specification creation" with guardrails and organizational principles, "Multi-step refinement, rather than one-shot code generation from a prompt", "Heavy reliance on advanced AI model capabilities". — [docs/how-to/sdd.md](https://raw.githubusercontent.com/github/spec-kit/main/docs/how-to/sdd.md)
- **spec-template.md required sections** (exact): header (Feature name, branch, created date, Status: Draft, original user description); **1. User Scenarios & Testing (mandatory)** — prioritized user stories (P1 most critical), "each should be testable on its own, so implementing one story yields a usable MVP"; for each story: journey, why this priority, independent test, Given/When/Then acceptance scenarios; Edge cases; **2. Requirements (mandatory)** — numbered FR-001…, `[NEEDS CLARIFICATION]` markers, Key Entities (what each represents and relationships, no implementation detail); **3. Success Criteria (mandatory)** — numbered SC-001…, measurable, technology-agnostic; **4. Assumptions** — reasonable defaults for unspecified details (target users, scope boundaries, reused systems, dependencies). Written "for business stakeholders". — [spec-template.md](https://raw.githubusercontent.com/github/spec-kit/main/templates/spec-template.md)
- **specify command rules**: "Make informed guesses based on context and industry standards"; mark `[NEEDS CLARIFICATION]` only when the choice significantly affects scope or UX, has multiple reasonable interpretations, or has no reasonable default; "LIMIT: Maximum 3 [NEEDS CLARIFICATION] markers total"; priority order "scope > security/privacy > user experience > technical details"; "Each requirement must be testable"; success criteria must be Measurable ("Include specific metrics (time, percentage, count, rate)"), Technology-agnostic, User-focused, Verifiable. Good example: "Users can complete checkout in under 3 minutes"; bad examples: "API response time is under 200ms", "React components render efficiently", "Redis cache hit rate above 80%". A `checklists/requirements.md` is generated and re-validated "until all items pass (max 3 iterations)". Commonly underspecified areas: "Feature scope and boundaries (include/exclude specific use cases)", "User types and permissions", "Security/compliance requirements (when legally/financially significant)". — [templates/commands/specify.md](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/specify.md)
- **clarify command**: purpose "Detect and reduce ambiguity or missing decision points in the active feature specification"; scans a fixed coverage taxonomy — Functional Scope & Behavior; Domain & Data Model; Interaction & UX Flow; Non-Functional Quality Attributes; Integration & External Dependencies; Edge Cases & Failure Handling; Constraints & Tradeoffs; Terminology & Consistency; Completion Signals; Misc/Placeholders — each marked Clear/Partial/Missing; "Maximum of 5 total questions across the whole session"; "Present EXACTLY ONE question at a time"; answers are logged to a Clarifications section and the spec is saved after each ("atomic overwrite"); prioritization "select the top 5 by (Impact * Uncertainty) heuristic". — [templates/commands/clarify.md](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/clarify.md)
- **plan-template.md sections**: Summary; Technical Context (Language/Version, Primary Dependencies, Storage, Testing, Target Platform, Project Type, Performance Goals, Constraints, Scale/Scope — each may be "NEEDS CLARIFICATION"); Constitution Check ("GATE: Must pass before Phase 0 research. Re-check after Phase 1 design."); Project Structure (docs: plan.md, research.md [Phase 0], data-model.md, quickstart.md, contracts/ [Phase 1], tasks.md [Phase 2, separate command]; source tree options single/web/mobile — "The delivered plan must not include Option labels"); Complexity Tracking ("Fill ONLY if Constitution Check has violations that must be justified"). — [plan-template.md](https://raw.githubusercontent.com/github/spec-kit/main/templates/plan-template.md)
- **tasks-template.md**: Phase 1 Setup; Phase 2 Foundational ("No user story work can begin until this phase is complete"); one phase per user story (goal, independent test, optional tests, implementation tasks, checkpoint); final Polish & Cross-Cutting (docs, cleanup, performance, security, quickstart validation). Task format `[ID] [P?] [Story] Description` (T001…, `[P]` = parallelizable because different files/no dependencies, `[US1]` labels); "every task should name exact file paths"; order: models → services → endpoints, core → integration; "Tests are OPTIONAL - only include them if explicitly requested in the feature specification"; "Each user story should be independently completable and testable"; MVP-first: complete Setup + Foundational + User Story 1, validate and demo, then add stories incrementally. — [tasks-template.md](https://raw.githubusercontent.com/github/spec-kit/main/templates/tasks-template.md)
- **constitution-template.md**: Core Principles (5 placeholders with examples: library-first, CLI interface, test-first "non-negotiable" red-green-refactor, integration testing, observability/versioning/simplicity); section for additional constraints (security, performance); section for development workflow / review / quality gates; Governance ("Constitution supersedes all other practices", "All PRs/reviews must verify compliance", "Complexity must be justified", "Amendments require documentation, approval, migration plan", versioning "MAJOR.MINOR.BUILD"). — [constitution-template.md](https://raw.githubusercontent.com/github/spec-kit/main/templates/constitution-template.md)
- Quickstart walkthrough guidance: constitution example "Taskify is a 'Security-First' application. All user inputs must be validated..."; specify = "Focus on the what and why, not the tech stack" (example spec names users, roles, sample data, "no login for this first phase"); clarify "before planning, optionally with a focus area"; plan is where "Implementation detail belongs"; `/speckit-checklist` generates "unit tests for your requirements"; `/speckit-analyze` is read-only cross-artifact consistency check — "Fix issues at the source, then re-run it before implementing"; implement "once for the whole feature, or one phase at a time for large features"; converge appends missing tasks until "Converged". Key principles: "Be explicit about what you're building and why. Keep tech stack out of the specification phase. Iterate on specs before implementation. Validate requirements and plans before coding. Let the coding agent handle implementation details." — [docs/quickstart.md](https://raw.githubusercontent.com/github/spec-kit/main/docs/quickstart.md)
- Contract-driven development (relevant to webhooks/integrations): agree the contract first, implement each side, verify both; a contract should cover "inputs, outputs, formats, validation rules, error cases, side effects, interaction guarantees (such as idempotency, ordering, retries, and timeouts), compatibility, versioning, and deprecation"; `/speckit.plan` produces feature-scoped `contracts/`; "Consumer tests against mocks are useful, but they don't prove the real provider conforms. Add provider verification and integration validation"; "A schema alone may not capture the full agreement, such as whether a retried request can create a duplicate"; OpenAPI is cited only as one example for public HTTP APIs. — [docs/how-to/contract-driven-development.md](https://raw.githubusercontent.com/github/spec-kit/main/docs/how-to/contract-driven-development.md)
- Large initiatives ("spec of specs"): "Reach for a spec of specs only when even a single phase is too large to handle in one run"; roadmap table columns ID / Sub-feature / Intent / Scope boundary / Depends on / Status / Sub-spec; slices must be "independently testable"; "Sharp boundaries are what keep each sub-spec small enough to fit in context"; "Keep the `ID` column immutable once a sub-spec references it"; independent slices can be built in parallel in separate worktrees; shared data model/contracts are handled only via scope-boundary notes (e.g., "assumes invoices exist"). — [docs/how-to/spec-of-specs.md](https://raw.githubusercontent.com/github/spec-kit/main/docs/how-to/spec-of-specs.md); complex features: limit a run to a task range (e.g., T001–T010) or one phase, mark `[X]` so the next run resumes; each sub-agent gets "one task plus the relevant plan excerpts, not the full feature context". — [docs/how-to/complex-features.md](https://raw.githubusercontent.com/github/spec-kit/main/docs/how-to/complex-features.md)
- Brownfield adoption: base the constitution on evidence (README, ADRs, contribution guide, CI); "Do not invent standards merely to fill the constitution template"; "unrealistic rules create noise instead of useful constraints"; pick "a bounded feature or modernization slice"; "You do not need to recreate an existing system from specifications before using Spec Kit." — [docs/how-to/existing-projects.md](https://raw.githubusercontent.com/github/spec-kit/main/docs/how-to/existing-projects.md)
- Spec Kit's own agentic SDLC: Assess → Specify → Plan/Tasks → Implement → Converge → Verify → Deploy (no agent) → Bugfix; human gate at every phase; "Running an agent on GitHub Actions does not make its reasoning a deterministic script"; "a new issue is untrusted input, not permission to run an agent"; maintainers "assess whether the patch and evidence address the stated need, not just whether the checks passed". — [docs/guides/agentic-sdlc.md](https://raw.githubusercontent.com/github/spec-kit/main/docs/guides/agentic-sdlc.md)

**Addy Osmani's spec-driven-development skill (retrieved 2026-11-07)**
- Gated workflow: "Each phase must be validated by the human before the next begins." Phase 0 Scope Check (capability map, only for multi-capability requests); Phase 1 Specify ("Surface assumptions, then write the spec. Stop the turn after saving it and wait for approval in a later turn"); Phase 2 Plan (`tasks/plan.md`); Phase 3 Tasks ("ordered tasks, each with acceptance criteria, a verification step, and files touched"); Phase 4 Implement (one task at a time, TDD). Spec template sections: Objective, Tech Stack, Commands, Project Structure, Code Style, Testing Strategy, Boundaries (Always / Ask first / Never), Success Criteria, Open Questions; "six core areas" = Objective, Commands, Project Structure, Code Style, Testing Strategy, Boundaries. Sizing: "A two-line spec is acceptable" for simple tasks but still needs acceptance criteria; "Each task should fit in a single focused session"; "No task should require changing more than about five files." Modular specs: capability map with stable kebab-case module ids, one-way dependencies ("If two modules each need the other, they are one module"), interface contracts recorded in the provider module's spec, files named `SPEC-identity.md`, `SPEC-billing.md`. — [addyosmani/agent-skills SKILL.md](https://raw.githubusercontent.com/addyosmani/agent-skills/main/skills/spec-driven-development/SKILL.md)
- Secondary summaries of Osmani's "How to write a good spec for AI agents" (page not opened): start with a high-level vision and let the AI draft `spec.md`; use a lightweight PRD with an objective "one or two sentences max"; save the approved spec as `SPEC.md`; split large work into scoped specs; cites the "curse of instructions" — "as you pile more requirements into an AI prompt, performance in adhering to each individual rule drops significantly". — [dev.to summary](https://dev.to/umesh_malik/the-300k-bug-that-was-never-the-ais-fault-inside-addy-osmanis-spec-framework-that-changes-43m5), [vibevibe mirror](https://vibevibe-mvp.pages.dev/en/Articles/04-engineering-practices/how-to-write-a-good-spec-for-ai-agents) (snippets)

**Harper Reed's "My LLM codegen workflow atm" (Feb 16, 2025; via Simon Willison's Feb 21, 2025 link post — neither page could be opened)**
- Three stages: (1) idea honing — a conversational model asks "one question at a time" until a detailed `spec.md` exists, saved in the repo; (2) planning — a reasoning model produces `prompt_plan.md` (LLM-generated prompts for each step, TDD, small iterative chunks) plus `todo.md` with lower-level steps that code models check off ("a neat hack for persisting state between multiple model calls"); (3) execution with a coding tool. ### Inferences
- The section set that is common to Spec Kit, Kiro, Osmani and cc-sdd — and therefore safest to use for a master spec — is: Goal/Why → Users & roles → Scope in/out → Prioritized, independently-testable user stories with Given/When/Then or EARS criteria → Numbered testable functional requirements → Key entities (data model) → Integration contracts (inputs/outputs/errors/idempotency/retries) → Non-functional requirements → Measurable, tech-agnostic success criteria → Assumptions → Bounded open questions → Standing rules (constitution/steering: Always / Ask first / Never) → Phased, dependency-ordered tasks with file paths.
- Every toolkit inserts a human approval gate between spec, plan and tasks; none recommends one-shot "build everything" prompts. A master prompt for the interior-design app should therefore be phrased as "produce SPEC.md and stop for approval", not "build the app".
- For a multi-integration app (ANDPAD/Teams/LINE), Spec Kit's contract-driven guidance and Osmani's capability map suggest: one roadmap with stable IDs, one sub-spec per integration, each with its own contract file, and explicit "assumes X exists" notes on cross-slice dependencies.
- Outcome evidence is anecdotal; the strongest reproducible signal is "specs reduce missed bugs at a token cost" plus consistent practitioner warnings about verbose specs and self-graded "done". Expect to budget reviewer time, not just agent time.

### Gaps
- Kiro's official `design.md` section list (Overview / Architecture / Components and Interfaces / Data Models / Error Handling / Testing Strategy) is widely quoted by third parties but could not be verified against kiro.dev in this session.
- No controlled, multi-developer study comparing SDD vs. plain prompting was found; the arXiv paper is conceptual, the dev.to study is n=1.
- Böckeler's own conclusions and Harper Reed's verbatim prompts could not be quoted because the hosts were blocked.

## Key Question 2 — Anthropic's official prompt-engineering guidance and Claude Code best practices (2025–2026)

### Takeaway
Anthropic's current (late-2026) Claude Code guidance has shifted from prompt tricks to three levers: (1) tell Claude what it cannot see from the repo (short CLAUDE.md ≤200 lines, specific prompts, a written SPEC.md produced by having Claude interview you), (2) give Claude a pass/fail check it can run (tests, typecheck, Stop hook, `/goal`, independent reviewer "against SPEC.md … skip style"), and (3) enforce no-exception rules deterministically (hooks, deny rules) rather than with CAPS in prompts. Older 2025 advice — "think hard" keywords, IMPORTANT emphasis, architecture descriptions in CLAUDE.md, "keep going/don't be lazy" — is explicitly listed as obsolete.

### Cited Findings

**Claude Code "Best practices" page (code.claude.com; current docs retrieved 2026-11-07; the former anthropic.com/engineering/claude-code-best-practices URL now 308-redirects here)**
- Diagnosis of failed sessions: "Claude built something different from what you had in mind… It's missing information it can't get from reading the repo"; "Claude said it was done and it wasn't quite, usually because it had no way to check its own work"; "Claude did something that must never happen… A prompt alone can't guarantee either of those." — [Best practices](https://code.claude.com/docs/en/best-practices)
- Deterministic vs non-deterministic: prompts, CLAUDE.md and skills are non-deterministic ("there's no guarantee that it'll follow your instructions"); hooks, deny rules, managed settings are enforced. "If you keep adding emphasis to a `CLAUDE.md` line and Claude still misses it, that's a sign the line belongs in a hook." — [Best practices](https://code.claude.com/docs/en/best-practices)
- Write a specific prompt — examples: instead of "fix the login bug" → "users report login fails after the session times out. look at token refresh in src/auth/, write a failing test that reproduces it, then fix it"; instead of "add a calendar widget" → "follow the pattern in HotDogWidget.php and build a calendar widget that lets you pick a month and page between years. no new libraries". Hand over artifacts rather than describing them (`@file`, pasted screenshots, piped logs). — [Best practices](https://code.claude.com/docs/en/best-practices)
- Scope phrasing that works: "`be ambitious`. Claude tends to read a request conservatively and build the smallest thing that satisfies it… When you want the fuller version… say so": example "build the settings page from the mockup. be ambitious: empty and error states, the save flow wired up, keyboard navigation, not just the layout". Phrases like "think step by step"/"be thorough" are "ordinary prompt text rather than keywords"; effort level is the real control. — [Best practices](https://code.claude.com/docs/en/best-practices)
- Brainstorm/interview to produce a spec: "I want to add rate limiting to the public API but haven't thought it through yet. Interview me until you could write the spec, then write it to SPEC.md." Claude "comes back with multiple-choice questions about the parts you haven't pinned down… It keeps asking until the answers add up to a spec." Then "start a fresh session to build from it, so the build begins with a clean context and a written definition of done." — [Best practices](https://code.claude.com/docs/en/best-practices)
- Keep CLAUDE.md short: include only "How to confirm work in this repo: the exact test, typecheck, and lint commands…", "Places where the code is misleading", "Decisions that aren't in the repo", "Anything you've had to correct twice already". Example file has three headings: `# Commands`, `# Conventions`, `# Gotchas`. Memory guide "recommends staying under 200" lines; `/init` drafts it, `/doctor` suggests cuts, `/doctor prompt-audit` flags stale/contradictory instructions. "If Claude keeps ignoring a line that *is* in `CLAUDE.md`, adding IMPORTANT probably won't fix it." — [Best practices](https://code.claude.com/docs/en/best-practices)
- Path-scoped rules: `.claude/rules/api.md` with `paths: ["src/api/**/*.ts"]` e.g. "Validate request bodies with the zod schemas in src/api/schemas/… Every new endpoint needs an entry in openapi.yaml, CI fails without it". - Give Claude a check to run: "Claude stops when the work looks done. If it has nothing to run that tells it whether the work actually *is* done, 'looks done' is all it has to go on." 'All tests pass' on its own tells you very little." — [Best practices](https://code.claude.com/docs/en/best-practices)
- Review against spec prompt: "use a subagent to review the rate limiter diff against SPEC.md, check every requirement is implemented and the listed edge cases have tests, report gaps that affect correctness and skip style" — "Don't drop the `skip style` part… A reviewer that's asked to find problems will always find *something*." - Enforce rules that can't have exceptions: `PostToolUse` prettier hook; `PreToolUse` hook blocking `migrations/`; permission `deny: ["Read(./.env)", "Read(./.env.local)", "Read(./secrets/**)"]`; sandbox. - Unattended runs — five questions: "1. Does it know what done looks like? A goal condition, a spec file, or a failing test it has to turn green. 2. Can it check its own work? … 3. What's it allowed to touch? … 4. What stops it? `--max-turns`, `--max-budget-usd`… 5. Where does the result go, and who signs off?" - Steering: "Watch the first minute, press `Esc` the moment Claude drifts, and after two failed corrections run `/clear` and write a better prompt instead of a third." ### Inferences
- For Claude Code specifically, the master prompt should be split into (a) a ≤200-line CLAUDE.md with Commands / Conventions / Gotchas / Boundaries, (b) a SPEC.md produced through an interview step, (c) `.claude/rules/*.md` for path-scoped API/webhook rules (e.g., "every new endpoint needs an entry in openapi.yaml"), (d) a reviewer subagent that checks diffs "against SPEC.md… skip style", and (e) hooks/deny rules for the few non-negotiables (never read `.env`, never touch migrations without review, typecheck before stop).
- The documented sample prompts (anti-overengineering, anti-test-gaming, investigate-before-answering, reversibility/ask-first) are the closest thing to official "known-good" phrasing for scope creep, hallucination and safety and can be pasted nearly verbatim into the master prompt's constraints section.
- Because older 2025 tricks are now officially deprecated, a 2026 master prompt should avoid ALL-CAPS/IMPORTANT, "think hard", "don't be lazy", and architecture dumps; instead it should name the exact commands that prove "done" and ask for evidence (command + output).

### Cited Findings

## Key Question 4 — Known failure modes of app-building prompts and recommended mitigations

### Takeaway
Documented failure modes cluster into: (1) missing or unverifiable definition of done (agent "marks its own homework"), (2) scope creep / over-engineering, (3) hallucinated or stale APIs/packages, (4) context drift across tasks (inconsistent error handling, naming, API shapes), (5) destructive or irreversible actions, and (6) over- or under-specification. Mitigations with primary-source backing: a runnable pass/fail check plus evidence, an independent reviewer against the spec, explicit scope/boundary clauses ("Always / Ask first / Never"), "investigate before answering" and contract-first integration with provider verification, deterministic hooks/deny rules, bounded clarification (≤3 markers / ≤5 questions), and sizing tasks to ≤5 files / one session.

### Cited Findings
- Definition-of-done failure: "Claude said it was done and it wasn't quite, usually because it had no way to check its own work"; mitigation = a check that "comes back pass or fail" and asking for evidence. — [Claude Code best practices](https://code.claude.com/docs/en/best-practices). Case study: the agent "marked its own homework and gave itself an A+". — [dev.to case study](https://dev.to/dimwiddle/ai-agents-cant-mark-their-own-homework-case-study-26mk) (snippet)
- Under-specification: Claude "tends to read a request conservatively and build the smallest thing that satisfies it" → say "be ambitious: empty and error states, the save flow wired up…". — [Claude Code best practices](https://code.claude.com/docs/en/best-practices). "If you want Claude to do more than the task strictly requires, explicitly request it." — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- Over-specification / instruction overload: "every line in [CLAUDE.md] takes a little of Claude's attention on *every* task"; >200 lines "reduce adherence"; contradictory instructions → "Claude may pick one arbitrarily". — [Claude Code memory](https://code.claude.com/docs/en/memory). "Minimal does not mean short… find the smallest set of high-signal tokens." — [Anthropic context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents). Osmani summaries cite the "curse of instructions" (adherence per rule drops as rules pile up). — [dev.to summary of Osmani](https://dev.to/umesh_malik/the-300k-bug-that-was-never-the-ais-fault-inside-addy-osmanis-spec-framework-that-changes-43m5) (snippet). Spec Kit limits ambiguity markers to 3 and clarify questions to 5 to avoid interrogation loops. — [specify.md](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/specify.md), [clarify.md](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/clarify.md)
- Scope creep / over-engineering: "Claude Opus 4.5 and Claude Opus 4.6 have a tendency to overengineer by creating extra files, adding unnecessary abstractions, or building in flexibility that wasn't requested" → the "Avoid over-engineering…" sample prompt. — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices). A May 22, 2026 essay describes scope creep as a runtime failure mode and proposes a "scope contract" where the agent declares goal, in-scope files, forbidden files and done criteria before starting. — [tianpan.co](https://tianpan.co/blog/2026-05-22-the-agent-that-wouldnt-stop) (snippet). Mitigations with official backing: `<investigate_before_answering>` ("Never speculate about code you have not opened"). — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices); give the agent the tool's `--help`/CLI or an MCP server for external systems; add docs/files with `@path`. — [Claude Code best practices](https://code.claude.com/docs/en/best-practices); contract-first integration with provider verification because "Consumer tests against mocks… don't prove the real provider conforms". — [Spec Kit contract-driven](https://raw.githubusercontent.com/github/spec-kit/main/docs/how-to/contract-driven-development.md). - Test-gaming / hard-coding: Claude "can sometimes focus too heavily on making tests pass at the expense of more general solutions" → sample prompt "Tests are there to verify correctness, not to define the solution." — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- Context drift across tasks: "エラー処理や命名、APIの形式がばらつき" when tasks get different context; error-response formats differ per feature. — [sam-solutions](https://sam-solutions.com/?p=50676) (snippet). Team-scale symptoms "存在忘却 / タイムループ / 記憶リセット". — [SpeakerDeck gotalab555](https://speakerdeck.com/gotalab555/claude-codehashi-yang-qu-dong-nomeng-wojian-nai) (snippet). Mitigation: constitution/steering files and path-scoped rules; "Every new endpoint needs an entry in openapi.yaml, CI fails without it". — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- Destructive/irreversible actions: "Without guidance, Claude Opus 4.6 might take actions that are difficult to reverse or affect shared systems, such as deleting files, force-pushing, or posting to external services" → reversibility prompt; deny rules hold "in every permission mode"; auto mode "does not guarantee safety". — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices), [Claude Code best practices](https://code.claude.com/docs/en/best-practices), [Permission modes](https://code.claude.com/docs/en/permission-modes)
- Security/compliance omission: Spec Kit asks about "Security/compliance requirements (when legally/financially significant)" only when no default exists and ranks "security/privacy" second in clarification priority. — [specify.md](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/specify.md). The quickstart's constitution example is a "Security-First" rule ("All user inputs must be validated"). — [quickstart.md](https://raw.githubusercontent.com/github/spec-kit/main/docs/quickstart.md). Claude Code recommends `deny: ["Read(./.env)", …]` and sandboxing. — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- "Build everything at once" failure: Spec Kit's tasks template enforces Setup → Foundational → one story at a time with "MVP-first"; Osmani caps tasks at "about five files" and "a single focused session"; Anthropic: "making steady advances on a few things at a time rather than attempting everything at once". — [tasks-template.md](https://raw.githubusercontent.com/github/spec-kit/main/templates/tasks-template.md), [Osmani SKILL.md](https://raw.githubusercontent.com/addyosmani/agent-skills/main/skills/spec-driven-development/SKILL.md), [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- Clarifying-question mechanics that work: "Interview me until you could write the spec" (Claude returns multiple-choice questions). — [Claude Code best practices](https://code.claude.com/docs/en/best-practices); "Present EXACTLY ONE question at a time", max 5, ranked by Impact × Uncertainty. — [clarify.md](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/clarify.md); Harper Reed's "one question at a time" brainstorming. — [Simon Willison](https://simonwillison.net/2025/Feb/21/my-llm-codegen-workflow-atm/) (snippet); autonomous/scheduled prompts "can't ask clarifying questions" so must state success and what to do with results. — [Common workflows](https://code.claude.com/docs/en/common-workflows)

### Inferences
- A master prompt should contain an explicit "Definition of Done" block listing the commands whose exit codes prove completion (typecheck, tests, lint, contract tests, a screenshot step for dashboards) and must demand evidence (command + output) in the final report.
- For integrations (ANDPAD, Teams, LINE webhooks), the strongest mitigation combination is: (a) require the agent to read the vendor docs/OpenAPI it is given and list assumptions before coding, (b) write the contract file (request/response/error/idempotency/retry/timeout) per integration first, (c) build against a mock/consumer test, then (d) run a provider-verification step against a sandbox tenant — because mocks alone "don't prove the real provider conforms".
- Put the five sample prompts from Anthropic (overengineering, test-gaming, investigate-before-answering, reversibility, subagent damping) into a `<constraints>` section; put zero-exception rules (never read `.env`, never run migrations against prod, never push to main) into hooks/deny rules, not prose.

- No peer-reviewed taxonomy of app-building prompt failures was retrievable (arXiv and several taxonomy blogs blocked); the Berkeley MAST multi-agent taxonomy was referenced in search results but not read, so its percentages are not cited.
- The 440,445-package hallucination statistic is quoted second-hand; the underlying study name was not confirmed.

## Key Question 5 — Phased delivery patterns and per-phase outputs

### Takeaway
Across Spec Kit, Kiro/cc-sdd, Osmani and Anthropic's docs the canonical phases are: constitution/steering → spec (approve) → clarify → plan + research + data model + contracts (approve) → tasks (Setup → Foundational → vertical user-story slices P1…Pn → Polish) → implement one story/phase per run with checks → converge/review against spec → PR with evidence. Per-phase artifacts named in primary sources are constitution.md, spec.md (user stories, FR-xxx, SC-xxx, assumptions, open questions), research.md, data-model.md, contracts/ (schemas/OpenAPI where appropriate, contract tests), quickstart.md, tasks.md (`[ID] [P] [US#]` with file paths), progress notes/`tests.json`, checklists, and a converge report. ADRs, ERDs, test plans and runbooks are recommended by practitioners but are not mandated artifacts in the official templates (except Spec Kit's brownfield guidance citing ADRs as constitution evidence).

### Cited Findings
- Spec Kit phase→artifact mapping: constitution (once) → spec.md → clarify (writes Clarifications section) → plan.md + research.md (Phase 0) + data-model.md + contracts/ + quickstart.md (Phase 1) → tasks.md (Phase 2) → checklists/requirements.md ("unit tests for your requirements") → analyze (read-only consistency) → implement (whole feature or "one phase at a time for large features") → converge (appends missing tasks until "Converged") → PR. — [quickstart.md](https://raw.githubusercontent.com/github/spec-kit/main/docs/quickstart.md), [plan-template.md](https://raw.githubusercontent.com/github/spec-kit/main/templates/plan-template.md)
- Vertical slicing in tasks: Setup → Foundational (blocking) → "one per user story (P1, P2, P3…)" each with goal, independent test, checkpoint → Polish & Cross-Cutting (docs, cleanup, performance, security, quickstart validation); "Complete Setup, Foundational, and User Story 1, then validate US1 independently and deploy or demo it." Within a story: tests first (if requested), "Models come before services, services before endpoints, and core work before integration." — [tasks-template.md](https://raw.githubusercontent.com/github/spec-kit/main/templates/tasks-template.md)
- Roadmap-level slicing for epics: sub-features must be "independently testable… implementing one leaves something demonstrable"; prerequisites first; independent slices in parallel worktrees; roadmap "names and orders sub-features but does not design them". — [spec-of-specs.md](https://raw.githubusercontent.com/github/spec-kit/main/docs/how-to/spec-of-specs.md)
- Kiro/cc-sdd phases: discovery (brief.md, roadmap.md) → requirements.md (EARS) → design.md (architecture, Mermaid, File Structure Plan) → tasks.md (`_Boundary:_`, `_Depends:_`) → autonomous impl with per-task review by subagents; humans approve at each phase gate. — [cc-sdd](https://github.com/gotalab/cc-sdd). Kiro official: requirements → design (architecture, sequence diagrams) → tasks; "Refine" propagates requirement edits into design and tasks. — [Kiro docs concepts](https://kiro.dev/docs/specs/concepts) (snippet). Size guide ≈7–10 requirements, ≈10–14 main tasks per spec. — [AWS builders-flash 202606](https://aws.amazon.com/jp/builders-flash/202606/organize-kiro-sdd-evolution/) (snippet)
- Osmani phases: Scope Check (capability map) → Specify (stop turn, await approval) → Plan (`tasks/plan.md`) → Tasks (acceptance criteria + verification step + files touched per task) → Implement (one task at a time, TDD; ≤~5 files per task). — [Osmani SKILL.md](https://raw.githubusercontent.com/addyosmani/agent-skills/main/skills/spec-driven-development/SKILL.md)
- Harper Reed: spec.md → prompt_plan.md (step prompts, TDD, small chunks) → todo.md checked off by the coding model. — [Simon Willison](https://simonwillison.net/2025/Feb/21/my-llm-codegen-workflow-atm/) (snippet)
- Anthropic: Interview → SPEC.md → fresh session to build → review diff against SPEC.md with a reviewer subagent → `/verify` builds and runs the app → PR; state tracking via `tests.json` + `progress.txt` + git; sub-agents return condensed summaries; compaction/notes for long runs. — [Claude Code best practices](https://code.claude.com/docs/en/best-practices), [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices), [Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Spec Kit's own SDLC adds Assess (go / needs-clarification / kill verdict) before Specify, Converge and Verify (`pr-assess` compares PR description with diff) after Implement, and keeps Deploy agent-free. — [agentic-sdlc.md](https://raw.githubusercontent.com/github/spec-kit/main/docs/guides/agentic-sdlc.md)
- Practitioner pattern (search snippets, pages not opened): "write or update the smallest useful design artifact before implementing, and… record architectural decisions in an ADR when they change"; a slice = "a thin end-to-end strip, such as one API endpoint, the form step that uses it, and the test that proves it"; done = "checkable mechanically, such as a passing test, a schema that validates, or an endpoint matching its contract… spec deviations surface through CI validation against the OpenAPI document"; ordered flow "architecture and ADR baseline, then vertical-slice builds, then verification against spec acceptance criteria, then quality gates". — [praneeth notes](https://notes.praneeth-suresh-s.workers.dev/topics/agent-coding/putting-it-together/), [alexop AFK coding](https://alexop.dev/posts/how-to-do-afk-coding), [javacodegeeks](https://www.javacodegeeks.com/?p=143212), [codex-conductor skill](https://termo.ai/skills/codex-conductor) (snippets)
- Brownfield phase advice: constitution from existing README/ADRs/CI; first feature = "a bounded feature or modernization slice", not an inventory of the whole system. — [existing-projects.md](https://raw.githubusercontent.com/github/spec-kit/main/docs/how-to/existing-projects.md)

### Inferences
- A phased master plan for the case-management app that matches the sources: Phase 0 constitution/CLAUDE.md + AGENTS.md; Phase 1 SPEC.md via interview (≤5 questions) with P1 = one end-to-end case lifecycle; Phase 2 plan with data-model.md (ERD as Mermaid, per cc-sdd/Kiro design.md practice), contracts/ per integration (OpenAPI for own API, vendor contract notes with idempotency/retry/timeout), research.md listing assumptions about vendor APIs; Phase 3 tasks.md with Setup → Foundational (schema, auth, error/response conventions, logging) → US1 vertical slice (create case → dashboard shows it) → US2 webhook ingest (mock then provider verification) → US3 Teams/LINE notifications → Polish (security, observability, runbook); Phase 4 implement per story with tests + evidence; Phase 5 converge + reviewer-against-spec + `/verify`.
- ADR/runbook/test-plan outputs are not demanded by any official template, so the master prompt must ask for them explicitly if wanted (e.g., "write `docs/adr/NNNN-*.md` for each decision that changes architecture; write `RUNBOOK.md` in the Polish phase").

### Gaps
- No primary source gives a numeric rule for how many vertical slices or how large a "Foundational" phase should be beyond Kiro's 7–10 requirements / 10–14 tasks heuristic (snippet) and Osmani's ≤5 files per task.
- The practitioner vertical-slice/ADR posts were only seen as search snippets.

## Key Question 6 — Highly regarded public "mega prompts" / spec templates for internal tools and dashboards, and Japanese-language resources

### Inferences — synthesized templates (each line traces to the sources above)

**Template A — Master spec skeleton (`SPEC.md`), sections and phrasing**
```
<context>            # why this app exists, who uses it, business constraints (Anthropic: explain why; Spec Kit: WHAT/WHY)
<users_and_roles>    # Spec Kit "User types and permissions" is a top underspecified area
<scope>              # In scope / Out of scope / Non-goals / Deferred (Spec Kit scope boundary column; Osmani Boundaries)
<user_stories>       # P1..Pn, each "independently completable and testable"; Given/When/Then or EARS
                     #   "WHEN <event> THE SYSTEM SHALL <response>" (Kiro EARS); P1 must be a usable MVP (Spec Kit)
<functional_requirements>  # FR-001.. "Each requirement must be testable" (Spec Kit)
<key_entities>       # names, attributes, relationships, no implementation detail (Spec Kit) → later data-model.md / Mermaid ERD (cc-sdd)
<integrations>       # per external system: inputs, outputs, formats, validation, error cases, side effects,
                     #   idempotency, ordering, retries, timeouts, versioning (Spec Kit contract-driven); link vendor docs to read first
<non_functional>     # perf, security/privacy, auditability, availability — from clarify taxonomy "Non-Functional Quality Attributes"
<success_criteria>   # SC-001.. measurable, technology-agnostic, user-focused (Spec Kit); SMART-style (Anthropic define-success)
<assumptions>        # defaults chosen instead of asking (Spec Kit "Assumptions")
<open_questions>     # max 3 [NEEDS CLARIFICATION], priority scope > security/privacy > UX > technical (Spec Kit)
<boundaries>         # Always / Ask first / Never (Osmani) + Anthropic reversibility prompt
<definition_of_done> # exact commands that must pass + evidence required (Claude Code "give Claude a check to run")
```

**Template B — Standing rules file (`CLAUDE.md` / `GEMINI.md` / `AGENTS.md`, ≤200 lines)**
```
# Commands      install / run one test / typecheck / lint / e2e / preflight (Anthropic example; Google GEMINI.md "preflight")
# Conventions   error helper, response envelope, naming, logging, i18n (sam-solutions drift warning; Anthropic example)
# Gotchas       env vars, misleading legacy dirs (Anthropic example)
# Boundaries    Always / Ask first / Never (Osmani); put zero-exception rules in hooks/deny rules instead (Anthropic)
# Workflow      plan first for multi-file changes; one story per run; report evidence (Spec Kit; Anthropic)
```

**Template C — Phase prompts (verbatim-backed)**
- Spec: "Interview me until you could write the spec, then write it to SPEC.md." (Anthropic) + "Present EXACTLY ONE question at a time… Maximum of 5" (Spec Kit clarify).
- Scope control: paste Anthropic's "Avoid over-engineering…" block; add "be ambitious: … not just the layout" for the stories you do want complete.
- Grounding: paste `<investigate_before_answering>`; add "read `docs/vendor/<api>.md` before touching `integrations/<api>/`; list every assumption about the vendor API in research.md".
- Safety: paste Anthropic's reversibility block; deny `.env`, migrations, force-push via hooks.
- Verify: "use a subagent to review the diff against SPEC.md, check every requirement is implemented and the listed edge cases have tests, report gaps that affect correctness and skip style" (Anthropic).
- Unattended: answer the five questions (done / check / allowed to touch / what stops it / who signs off) before `claude -p … --max-turns N`.

**Template D — Task line format**: `T017 [P] [US2] Add LINE webhook signature check in src/integrations/line/verify.ts` (Spec Kit `[ID] [P?] [Story] Description` with exact file path; cc-sdd adds `_Boundary:_` / `_Depends:_`).
