## Q1. Messaging API: webhook event types, reply/push/multicast/broadcast, rate limits, signature verification, retry/redelivery, content retrieval, user profiles, group-chat visibility

### Takeaway
The Messaging API delivers every user-side event for a LINE公式アカウント to a single HTTPS Webhook URL (verify `X-Line-Signature` HMAC-SHA256, de-duplicate on `webhookEventId`, and expect out-of-order redelivery); a bot can be invited into group chats once the "allow group participation" setting is enabled, after which it receives the group's message events and can look up member profiles/IDs. Exact numeric rate limits, reply-token validity and the verified-account restriction on group member ID retrieval could not be confirmed from the official pages in this session and must be checked at developers.line.biz before coding.

### Cited Findings
- [公式] When a user adds the account as a friend or sends a message, the LINE Platform sends an HTTP POST to the Webhook URL registered in the LINE Developers Console; the docs warn that a received POST may not have come from LINE, so signature verification is required, and asynchronous event processing is recommended — [LINE Developers: メッセージ（Webhook）を受信する](https://developers.line.biz/ja/docs/messaging-api/receiving-messages/) (as surfaced in search excerpts, 2026)
- [公式] `memberJoined` is "Event object for when a user joins a group chat or multi-person chat that the LINE Official Account is in"; the payload contains `joined` (members) plus common fields such as `webhookEventId` — [LINE webhook SDK model derived from the official spec (docs.rs line_webhook 1.0.3)](https://docs.rs/crate/line_webhook/latest/source/src/models/member_joined_event.rs)
- [公式] Webhook redelivery: "The Messaging API provides a feature to redeliver webhooks that your bot server fails to receive" (e.g., temporary overload); the feature is available on all Messaging API channels; use `webhookEventId` to detect duplicates; `deliveryContext.isRedelivery` indicates a redelivered event; "If the LINE Platform redelivers webhooks, the order of webhook events you receive can be different from the order the events occurred" — [LINE Developers: Receive messages (webhook)](https://developers.line.biz/en/docs/messaging-api/receiving-messages/)
- [公式] Webhook redelivery was announced on 2022-03-07 as being added "in early April 2022" — [LINE Developers news 2022-03-07](https://developers.line.biz/en/news/2022/03/07/pre-release-webhook-redelivery/)
- A redelivered event keeps the same `webhookEventId`; only `deliveryContext.isRedelivery` changes — [Hookdeck guide to LINE webhooks](https://hookdeck.com/webhooks/platforms/guide-to-line-webhooks-features-and-best-practices) (third party)
- Third-party note (older, unverified): redelivery may be off by default in the LINE Developers Console and the number/interval of retries is not published — [deeple.ai tutorial on enabling webhook redelivery](https://tutorials.deeple.ai/faq/line-oa/webhook-redelivery-line-developers)
- [公式] Development guidelines: keep requests under the published rate limits; exceeding them returns `429 Too Many Requests`; the guidelines recommend signature validation rather than IP allow-listing for authenticating webhooks — [LINE Developers: Messaging API development guidelines](https://developers.line.biz/en/docs/messaging-api/development-guidelines/)
- The webhook signature is an HMAC-SHA256 over the raw request body using the channel secret; verify before processing — [SleekFlow: LINE Messaging API guide](https://sleekflow.io/en-us/blog/line-messaging-api.md) (third party)
- Reply-token validity — sources conflict: SleekFlow says LINE instructs to use the reply token "within one minute of the webhook" and may change this without notice — [SleekFlow](https://sleekflow.io/en-us/blog/line-messaging-api.md); a third-party course module claims a 5-minute window from the 200 OK — [LINE_OA_DEV module 8](https://than-is-on.duckdns.org/LINE_OA_DEV/module-08-webhook.html). A reply token can be used once — [SleekFlow](https://sleekflow.io/en-us/blog/line-messaging-api.md)
- A 2024 developer scrap confirms `429 Too Many Requests` when sending over the rate limit and shows adding wait logic between sends — [Zenn scrap (nakaaa)](https://zenn.dev/nakaaa/scraps/d4f265badcfe47)
- A LINE-integration vendor documents that one text message is limited to 5,000 characters and that some message types cannot be handled "due to the LINE API spec" — [Zaapi: LINE limitations](https://help.zaapi.com/integrations/line/limitations)
- [公式] Group chats: "LINE公式アカウントは、Messaging APIを使用してグループトークや複数人トーク内のユーザーと対話できます"; since LINE 10.17.0 multi-person chats were merged into group chats; the docs state that the account can obtain information about the group it belongs to and about its members — [LINE Developers: グループトーク](https://developers.line.biz/ja/docs/messaging-api/group-chats/)
- [公式] "ユーザーIDを取得する" lists obtaining user IDs from webhooks and "グループトークや複数人トークのメンバーのユーザーIDを取得する" as supported methods — [LINE Developers: ユーザーIDを取得する](https://developers.line.biz/ja/docs/messaging-api/getting-user-ids/)
- A LINE公式アカウント cannot join group chats by default; the "グループ・複数人トークへの参加を許可する" setting must be enabled (described as under LINE Official Account Manager「機能の利用」/ Messaging API settings) — [success.dx-line.com: チャット利用の基本](https://success.dx-line.com/?p=229); invitation walkthrough — [tgg.jugani-japan.com](https://tgg.jugani-japan.com/tsujike/linegroup1/)
- A working example of a bot placed in a LINE group that reacts only to specific keywords (implying it receives every message event in the group and filters server-side) — [Qiita: LINEのチャットbotをグループに参加させて特定キーワードのみ反応させる (GAS)](https://qiita.com/yuta-matsumoto/items/8fb00eabe8168f3dfeab)
- [公式] Content sent by users (images/video/audio/files) is "automatically deleted after a certain period" (period not stated); guides recommend retrieving and storing content at webhook time — [LINE Developers receiving-messages page as summarised in search](https://developers.line.biz/ja/docs/messaging-api/receiving-messages/); endpoint pattern `GET https://api.line.me/v2/bot/message/{messageId}/content` with a Bearer channel access token, and `api-data.line.me` for content/preview — [fromation.co.jp blog](https://anything.fromation.co.jp/archives/45238) (third party; verify against reference)
- [公式] The Messaging API reference (Japanese) is at [developers.line.biz/ja/reference/messaging-api](https://developers.line.biz/ja/reference/messaging-api); the overview at [developers.line.biz/ja/docs/messaging-api/overview/](https://developers.line.biz/ja/docs/messaging-api/overview/)
- [公式] "Mark as read" (既読にする) is documented under *partner docs* (i.e., restricted to LINE partners), so an ordinary channel cannot programmatically mark a user's message as read — [LINE Developers partner-docs: mark as read](https://developers.line.biz/ja/docs/partner-docs/mark-as-read/)
- For push messages the sender needs the recipient's userId ("U" + 32 hex, 33 chars) and the recipient must have added the account as a friend — [Yoom help on LINE Notify replacement](https://intercom.help/yoom/ja/articles/10442086)
- A profile lookup returns display name, picture URL and status message and is used as the anchor for matching to in-house customer records — [ONEDER (Hakuhodo DY ONE) explainer](https://oneder.hakuhodody-one.co.jp/blog/linemessagingapi) (third party)

### Inferences
- For a case-management mirror, the safe design is: one webhook endpoint → immediate 200 → enqueue → idempotency on `webhookEventId` → immediately fetch binary content for image/video/file messages (because LINE deletes it after an unpublished period) and store it in your own storage → sort by `timestamp` not arrival order.
- Because message events in a group chat carry `source.groupId` plus `source.userId`, a bot in a per-project group can mirror all customer and staff messages, but it only sees events from the moment it joined (no history API exists in any source found).
- Since "mark as read" is partner-only, an internal tool that replies via push cannot clear the unread badge on the OA Manager side; the read state in your internal app is independent.

### Gaps
- Exact numeric rate limits (recollection: push/reply/multicast ~2,000 req/s, broadcast/narrowcast ~60 req/h, get-content ~2,000 req/s; profile endpoints 2,000 req/s) — NOT verified here; check [Messaging API reference → Rate limits](https://developers.line.biz/en/reference/messaging-api/#rate-limits).
- Full webhook event-type list (message, unsend, follow, unfollow, join, leave, memberJoined, memberLeft, postback, videoPlayComplete, beacon, accountLink, things, membership, delivery) — recollection; verify at [Webhook event objects](https://developers.line.biz/en/reference/messaging-api/#webhook-event-objects).
- Whether "Get group chat member user IDs" (`GET /v2/bot/group/{groupId}/members/ids`) is restricted to verified/premium accounts — recollection says yes; not confirmed; verify at the reference above. Member *profile* lookup and group summary are believed available to all accounts (unverified).
- Content retention window for the get-content endpoint — not published in any source found.
- Multicast cap (recollection: 500 userIds per request) and whether reply messages are free of quota — see Q2; not re-verified.
- Redelivery schedule (how many retries, over how long) — not published.

## Q2. Pricing, plans and message quotas (コミュニケーション / ライト / スタンダード; 2023 and 2026 revisions)

### Takeaway
Since 2023-06-01 (Japan only) the plans are コミュニケーション ¥0/月 with 200 free messages, ライト ¥5,000/月 with 5,000 messages (no add-on messages), and スタンダード ¥15,000/月 with a larger allowance plus pay-per-message add-ons; on 2026-10-01 the add-on pricing for スタンダード changed from a multi-tier declining scale to a two-tier scale (¥3/通 up to 200,000 通, ¥2.5/通 beyond, 税別) while fixed fees and free allowances stayed unchanged. Messaging API push/multicast/broadcast consume this same quota; replies and manual chat do not (widely reported; official page not fetchable here).

### Inferences
- For a customer-support use case (reply-heavy, low broadcast volume), the free コミュニケーションプラン or ライトプラン is usually sufficient, because replies via reply token and manual chat replies do not count; only proactive pushes from the internal tool (e.g., staff answering later via push, status notifications) consume the 200/5,000 allowance. Count pushes per recipient per message.
- ライト has a hard ceiling (no add-ons), so an internal tool that pushes notifications must either throttle or the account must be on スタンダード.

## Q3. Can one LINE公式アカウント run both human「チャット」replies and Messaging API bot replies? Rules as of 2026, multi-tool constraints, and staff-reply-from-internal-tool architectures

### Takeaway
Yes. Since 2022-11-30 the old 応答モード (Bot or チャット) was removed and 応答設定 now has independent toggles — チャット on/off, あいさつメッセージ, 応答メッセージ, Webhook — so manual chat in LINE Official Account Manager and Messaging API webhooks can run together on one account (official LINE Developers news; confirmed by multiple vendor write-ups). Constraints: only one Webhook URL per channel, channel access tokens have issuance limits, and some blogs still describe the pre-2022 either/or behaviour (outdated/contradictory).

### Cited Findings
- [公式] From 2022-11-30 a LINE公式アカウント can use Webhook and チャット together; the former 応答モード setting (Bot mode for Webhook vs チャット mode) was replaced by a チャット on/off switch; existing accounts in チャット mode became チャット=on, those in Bot mode became チャット=off — [LINE Developers news 2022-12-01: use both chats and webhooks](https://developers.line.biz/ja/news/2022/12/01/use-both-chats-and-webhooks/) (as summarised in search results)
- Classmethod engineers confirmed (article dated after the Dec-2022 spec change) that manual chat and Webhook can be combined: automate routine exchanges and have humans reply to non-routine ones from the chat screen — [DevelopersIO: LINE公式アカウントで手動チャットとWebhookを併用](https://dev.classmethod.jp/articles/line-chat-webhook)
- Setup path used by vendors for API integration: LINE Official Account Manager →「設定」→「応答設定」→ turn「応答メッセージ」off (when the API controls auto-replies) → turn「Webhook」on; あいさつメッセージ optional — [ligla.jp API integration guide](https://ligla.jp/blog/line-official/apiintegration/); same procedure (enable both チャット and Webhook) — [grandream.jp](https://www.grandream.jp/blog/line-webhook-with-chat)
- Vendor explainers of the same change: [SocialPLUS: LINEチャットと拡張ツール/MAの併用が可能に](https://blog.socialplus.jp/knowledge/line-chat-and-external-tools/); [autosns.co.jp: botとチャットの併用方法](https://autosns.co.jp/blog/chat-in-bot/); [linexat.com](https://linexat.com/webhook/); [eightsumarketing.co.jp](https://eightsumarketing.co.jp/blog/line-specification-change/); [maxmouse.co.jp 2023-01-13 summary of Dec-2022 changes](https://www.maxmouse.co.jp/tips/2023/0113_2/)
- Contradicting/outdated claim: an Aurant Technologies article asserts a "dilemma" where enabling Webhook may make the OA Manager chat unusable or stop notifications — [aurant-technologies.com ?p=15995](https://aurant-technologies.com/?p=15995). This conflicts with the official 2022-12-01 news and Classmethod's test; treat as outdated.
- Tool-specific caveat: Poster (a LINE tool) notes that friends who were added while the account was in the old チャット mode are not recognised by the tool — [poster.ooo FAQ](https://poster.ooo/faq/use-two-system/)
- [公式] 2026-07-23 LINE Developers tips on using multiple API tools with one account: only one Messaging API channel is linked to an OA; "［Webhook URL］に設定できるURLは1つのみ"; when sharing a channel, check which type of channel access token each tool uses, because tokens with an issuance cap can be invalidated/affected by another tool's issuance or re-issuance; inventory which tools only send vs. also need webhook receipt — [LINE Developers tips 2026-07-23](https://developers.line.biz/ja/tips/2026/07/23/using-multiple-api-tools/)
- Webhook-forwarding (Webhook転送) tools are the standard workaround for the single-URL limit; channel, Webhook URL, token limits and rate limits are shared across tools — [SocialPLUS: 複数のLINE拡張ツールを併用する方法](https://blog.socialplus.jp/knowledge/use-multiple-line-tools/); [poster.ooo blog](https://poster.ooo/blog/line-webhook-with-tools/); [UnifyPort checklist](https://www.unifyport.ai/ja/blog/line-messaging-api-multiple-tools-one-official-account/); [dev.to/unifyport](https://dev.to/unifyport/one-line-official-account-multiple-tools-webhook-and-token-architecture-3p5l); GAS/PHP relay example — [kousha.jp 2025-04-01](https://www.kousha.jp/2025/04/01/webhook/)
- [公式] "Mark as read" API is partner-only — [partner-docs](https://developers.line.biz/ja/docs/partner-docs/mark-as-read/)

### Inferences
- Recommended architecture for the case-management app: keep チャット=on (so staff can still use the OA Manager app as a fallback and see history), Webhook=on, 応答メッセージ=off; the internal app receives every inbound event via webhook, and staff reply from the internal app via push (userId or groupId). Replies within the reply-token window can use the free reply endpoint; later replies must be pushes and count toward quota.
- If other LINE tools (e.g., Lステップ/Liny-type MA) are in use, the internal app must sit behind a webhook relay or be the relay itself, because only one Webhook URL is allowed.

### Gaps
- Whether messages pushed via the Messaging API appear in the OA Manager chat timeline, and whether messages sent manually from the chat screen generate any webhook (recollection: API-sent messages do appear in the chat screen after the 2022-11-30 change; manually sent messages do NOT trigger a webhook, so an internal mirror cannot capture staff replies typed in OA Manager) — NOT confirmed; verify at the 2022-12-01 news and the receiving-messages page.
- Whether a user can be "handed over" between bot and human (e.g., 手動チャットに切り替え) is an app-side state, not a LINE setting — no official source found.

## Q4. Rich menu, LIFF apps (問い合わせ / アフター依頼 / 写真送付), Flex Messages, LINE Login for identifying customers, 友だち追加 via QR per project

### Takeaway
Rich menus are the standard entry point to LIFF forms; LIFF gives `liff.getProfile()` (userId/displayName), `liff.sendMessages()` (up to 5 messages, only in the LINE in-app browser launched from a 1:1 chat), and server-side ID-token verification for trustworthy identification, which lets a form submission be tied to the same userId that the Messaging API sees. Per-user rich menu APIs, rich-menu aliases, Flex limits and per-project QR tracking could not be verified in this session.

### Cited Findings
- [公式] LIFF was announced 2018-06-06 so that customer-info input and ordering that previously required jumping to an external web page can run seamlessly inside the LINE app — [LY Corp press release PDF 2018-06-06](https://www.lycorp.co.jp/news/archive/L/ja/ja20180606_A.pdf)
- [公式] LIFF developer guide — [developers.line.biz/en/docs/liff/developing-liff-apps/](https://developers.line.biz/en/docs/liff/developing-liff-apps/)
- `liff.getProfile()` returns userId and displayName (pictureUrl/statusMessage if set) and requires the profile scope; `liff.sendMessages()` sends up to 5 messages on the user's behalf into the chat room from which the LIFF app was opened and only works for LIFF apps launched from a 1:1 chat; `liff.sendMessages()`/`liff.scanCode()` do not work in external browsers, so check `liff.isInClient()`; server-side identification can use the ID token with `POST /oauth2/v2.1/verify` — [doggy8088 liff-v2-snippets README (mirrors official API)](https://github.com/doggy8088/liff-v2-snippets/blob/master/README.md); [LINE Engineering blog: LIFF](https://engineering.linecorp.com/en/blog/liff-our-latest-product-for-third-party-developers/); [linebot.pro LIFF guide 2026](https://linebot.pro/blog/liff-app-development-guide)
- LINE's engineering sample shows a LIFF app generating an image (signature pad), calling `liff.getProfile()` for the sender name and `liff.sendMessages` with `type: 'image'` — [LINE Engineering blog](https://engineering.linecorp.com/en/blog/liff-our-latest-product-for-third-party-developers/)
- Rich menu → LIFF: the simplest way to build a rich menu is LINE Official Account Manager (choose template, upload image, set an action per tap area); LIFF URLs must be registered as LIFF apps, with care when navigating between pages — [CodeZine 17908](https://codezine.jp/article/detail/17908)
- Segmented rich menus (show a specific menu only to users who answered a survey) are offered by MA tools such as L Message — [lme.jp manual](https://lme.jp/manual/?p=27277) (vendor)
- Make's LINE app exposes modules for creating/deleting rich menus, downloading user attachments and getting group/room member profiles — [make.com LINE integration page](https://www.make.com/en/integrations/line/zapier) (vendor)
- A 2026 工務店 guide describes a flow of sharing site-progress photos with the 施主 where only approved photos are delivered — [aurant-technologies: リフォーム・工務店のLINE活用ガイド 2026](https://aurant-technologies.com/blog/line-official-account-for-reform-koumuten/) (vendor)
- A 2024-07-10 Lステップ case: a house maker in 山陰 built an operation that exchanges drawings and estimates over LINE — [linestep.jp 2024-07-10](https://linestep.jp/2024/07/10/lstep-case-house-maker/) (vendor case)

### Inferences
- For 写真送付, two patterns work: (a) the customer simply sends an image in the 1:1 chat → `message` event with `type: image` → fetch content and attach to the case; (b) a LIFF form with `<input type="file" accept="image/*">` uploading straight to your server, with the userId from the verified ID token — pattern (b) gives structured metadata (案件, 箇所, 種別) while (a) is zero-friction.
- Because the LIFF/LINE Login userId equals the Messaging API userId only when the LINE Login channel and Messaging API channel sit under the same provider (recollection, unverified), create both channels under one provider from the start.

### Gaps
- Per-user rich menu linking (`POST /v2/bot/user/{userId}/richmenu/{richMenuId}`), rich menu alias/tab switching, limits (recollection: up to 1,000 rich menus per channel, up to 20 tap areas), Flex Message size limits, and 友だち追加 QR with 流入経路分析 parameters — none verified; check [Messaging API reference: Rich menu](https://developers.line.biz/en/reference/messaging-api/#rich-menu) and OA Manager help for 流入経路分析.
- Same-provider userId equivalence between LINE Login and Messaging API — verify at [developers.line.biz "User IDs"](https://developers.line.biz/en/docs/line-login/overview/).

## Q5. LINE WORKS as alternative/complement: 外部トーク連携 with LINE users, APIs, pricing, when to choose it

### Takeaway
LINE WORKS lets staff talk with ordinary LINE users from their own LINE WORKS talk rooms (外部トーク連携), usable even on the free plan after a 7-day waiting period, with talk audit logs kept 180 days; LINE users get talk only (no calls), and reported limits are 30 LINE users per room. Pricing (third-party listings): フリー ¥0 (30 users), スタンダード ¥540/user/月 (¥450 annual), アドバンスト ¥960 (¥800 annual). It suits staff-to-施主/協力業者 chat with compliance logging, but has no public "LINE user webhook" equivalent to the Messaging API for mirroring customer conversations into your own app (not confirmed either way).
