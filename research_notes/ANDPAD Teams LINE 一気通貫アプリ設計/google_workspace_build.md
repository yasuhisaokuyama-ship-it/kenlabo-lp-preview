## Key Question 1 — Build options compared: (1) Apps Script + Sheets + Looker Studio, (2) AppSheet, (3) Cloud Run + Firestore/BigQuery + web front end, (4) Google Chat apps / Workspace add-ons

### Takeaway
Apps Script web apps cannot read inbound HTTP headers (per multiple independent developer sources and working repos), so they cannot verify the LINE `x-line-signature` or the Teams `Authorization: HMAC …` header — the single biggest reason to put the **webhook receiver on Cloud Run** (or another real HTTP server) even if the rest of the app stays in Sheets/Looker Studio/AppSheet. Cloud Run + Firestore is effectively free at this scale (2M requests/month and 50k Firestore reads/day free), and since March 2026 Cloud Run has a one-flag IAP integration ("recommended authentication mechanism for internal business applications") that gives Google-identity login without a load balancer. Google Chat incoming webhooks are one-way (post-only) and cannot receive messages.

### Cited Findings

**Apps Script (GAS) quotas and limits**
- Apps Script quotas (Google Workspace account vs consumer): script runtime **6 min / execution** (both); triggers total runtime **6 hr / day** (Workspace) vs 90 min / day (consumer); URL Fetch calls **100,000 / day** (Workspace) vs 20,000 / day (consumer); Google states limits "are subject to change at any time without notice"; quotas are per user and reset 24 hours after the first request — [Apps Script quotas (developers.google.com), via search snippet 2026-11-07](https://developers.google.com/apps-script/guides/services/quotas)
- `doPost(e)` in Apps Script has no property that exposes HTTP request headers; a 2018 teratail answer states "doPost()のパラメータオブジェクトにHeader情報を直接取得できるプロパティはない" and suggests moving the signature into the query string instead — [teratail Q117983, via search snippet (third-party, 2018)](https://teratail.com/questions/117983)
- A Japanese technical article (issoh.co.jp) states GAS `doPost(e)` does not receive request headers, so header-based signatures cannot be verified, making GAS unsuitable as the receiver for signed webhooks — [issoh.co.jp tech article, via search snippet (third-party)](https://www.issoh.co.jp/md/tech/1378)
- A working GAS LINE-webhook repo (`gas/line_webhook_gas.js`) explicitly comments that `doPost(e)` cannot read HTTP headers, so `X-Line-Signature` verification "is not possible here" and the channel secret is unused; it mitigates abuse only by capping processed events at 10 per request and stores `LINE_CHANNEL_ACCESS_TOKEN` in `PropertiesService.getScriptProperties()`; replies go via `UrlFetchApp.fetch("https://api.line.me/v2/bot/message/reply")` with `Authorization: Bearer <channel access token>` — [coseto6125/papaking line_webhook_gas.js (GitHub, fetched 2026-11-07)](https://github.com/coseto6125/papaking/blob/3c594bf9e4340ab77c1ba6c98a5b1cd39dd32cd7/gas/line_webhook_gas.js)
- A GAS "webhook relay" repo computes HMAC with `Utilities.computeHmacSignature` over the raw `e.postData.contents` (SHA-256 or SHA-1), hex-encodes, strips `sha256=`/`v1=` prefixes, and returns 401 on mismatch — but it reads the signature from `e.parameter[...]` (query/form param) first, with a comment that in GAS "headers may be passed via e.parameter"; it also notes that constant-time comparison is not possible in GAS — [mongsill6/gas-webhook-relay Code.gs (GitHub, fetched 2026-11-07)](https://github.com/mongsill6/gas-webhook-relay/blob/d9265dc8f08fde411d0b2f5ff9104efed53276c0/Code.gs)
- Apps Script can accept inbound JSON through `doPost(e)` published as a web app URL and append a row to a sheet (minimal example in a Pipedrive community thread) — [devcommunity.pipedrive.com, via search snippet (third-party)](https://devcommunity.pipedrive.com/t/using-google-app-scripts-for-automation-integration/4959)

**Looker Studio (dashboard layer)**
- Looker Studio conditional formatting is positioned as a way to highlight data by condition (e.g., sales above target in green; KPI alerts at thresholds) — the only Japanese source found describes the concept, not a 信号機 (red/yellow/green) step-by-step; it also recommends color-universal design (not relying on red/green alone) — [Hakky, Looker Studio 条件付き書式, via search snippet (third-party)](https://book.st-hakky.com/data-analysis/looker-conditional-formatting); related English how-to: [databloo (via search snippet, not fetched)](https://www.databloo.com/blog/google-looker-studio-conditional-formatting/)

**Google Chat apps / incoming webhooks**

**Cloud Run + Firestore (pricing, auth)**

### Inferences
- For a 30-user company the compute/storage cost of option (3) is dominated by $0 free tiers (2M requests, 50k reads/day); a few thousand webhooks/month is <1% of the Cloud Run request free tier. The real recurring costs are Workspace seats (already paid) and AI tokens.
- Recommended hybrid for an AI coding agent to specify: **Cloud Run (Node/Python) receives LINE/Teams webhooks and verifies signatures with raw-body HMAC-SHA256**, writes normalized events to **Firestore (default DB, asia-northeast1)**; a scheduled job (Cloud Scheduler → Cloud Run, or an Apps Script time trigger within the 6 hr/day trigger budget) computes 案件 status and "unanswered inquiry" flags; dashboard served either by the same Cloud Run app behind IAP, or by Sheets + Looker Studio fed from Firestore/BigQuery for the 信号機 view.
- Apps Script remains viable for *outbound* integrations (UrlFetchApp to LINE/Teams/ANDPAD, 100k calls/day) and for Sheets-centric business logic, but not as the authenticated webhook ingress. Where GAS must receive a webhook, the only mitigation documented in the wild is an unguessable URL plus event-count caps — not cryptographic verification.
- AppSheet is a good UI layer for field staff (mobile, offline, photos) on top of Sheets/Cloud SQL, but its 2026 price moves and the inability to verify webhook signatures inside AppSheet automation (no evidence found that it can) mean it should consume data, not receive raw webhooks.
- Google Chat is only useful for *notifying* staff (incoming webhook) or for a full Chat app; it cannot replace the LINE/Teams inbound path.

- The official Apps Script **web apps** page (redirect behaviour for POST, no custom status codes, "Execute as"/"Who has access" wording) could not be fetched; the "no headers in doPost" fact rests on consistent third-party evidence (2018–2026), not on a quoted Google statement.
- Apps Script 2025–2026 release notes (runtime/quota changes) could not be retrieved (`developers.google.com` blocked).
- Official AppSheet pricing page, "AppSheet Core included in Workspace editions" confirmation, and "Gemini in AppSheet" feature/pricing details were not retrievable.
- Cloud Run **request-based CPU** unit price for Tier 1 was not cleanly extractable from the page dump (only memory $0.0000025/GiB-s and $0.40/M requests were); Firestore per-100k-operation prices for asia-northeast1 were not extracted.
- Workspace add-ons (Gmail/Drive side panels) were not researched beyond Chat webhooks.

## Key Question 2 — AI inside the Google boundary: Gemini on Vertex AI (data-use, no-training, Japan region) and Claude on Google Cloud

### Takeaway
Google Cloud's Service Specific Terms (last modified 2026-04-02) contractually state Google will not use Customer Data to train AI/ML models and will not store prompts/outputs beyond what is needed to generate output; Tokyo data residency is documented for Gemini 2.5 Flash/Pro but Gemini 3-series availability in asia-northeast1 is unconfirmed. Claude is available two ways inside a GCP project: **Google-managed (Vertex/Agent Platform)** where Google is the data processor and regional endpoints exist (but only for Sonnet 4.6 and earlier; newer models need global/multi-region), and **Anthropic-managed** (`claude.googleapis.com`, Marketplace billing) which follows Anthropic's first-party retention and offers only `global`/`us` inference geos — neither offers a Japan-pinned region for current Claude models.

### Cited Findings

**Google Cloud contractual data governance (official)**
- Section 18 (Training Restriction): "Google will not use Customer Data to train or fine-tune any AI/ML models without Customer's prior permission or instruction." Section 20(a): "Generated Output is Customer Data." Section 20(h): absent permission, Google "will not store outside Customer's Account (i) Customer Data prompted to a Generative AI Service for longer than is reasonably necessary to create the Generated Output, or (ii) the Generated Output." Section 16 (AI/ML Data Location): customer may configure storage at rest and ML processing in a specific Multi-Region. Exceptions: Grounding with Google Search stores derived query logs "for up to three (3) days"; Grounding with Google Maps stores prompts/outputs for 30 days. Page shows "Last modified April 2, 2026" — [Google Cloud Platform Service Specific Terms (cloud.google.com/terms/service-terms), fetched 2026-11-07](https://cloud.google.com/terms/service-terms)
- Google's Vertex AI data residency page states "Google Cloud only stores customer data in the region that you specify for all generally-available features of Generative AI on Vertex AI" and lists **Tokyo (asia-northeast1)** among Asia-Pacific locations for Gemini 2.5 Flash and 2.5 Pro — [Vertex AI generative AI data residency, via search snippet](https://cloud.google.com/vertex-ai/generative-ai/docs/learn/data-residency)
- Gemini 3 Pro (preview, `gemini-3-pro-preview`) is listed under the **global endpoint** tab of the locations page; a Google developer-forum thread says the preview is only available via the global Vertex endpoint — [Vertex AI locations page, via search snippet](https://cloud.google.com/vertex-ai/generative-ai/docs/learn/locations); [discuss.google.dev thread (404 for gemini-3-pro-preview in europe-west8)](https://discuss.google.dev/t/404-not-found-unable-to-access-vertex-ai-gemini-3-pro-preview-in-europe-west8/288743)
- A third-party Japanese analysis (Sept 2026) claims the Tokyo column of Google's locations table marks Gemini 2.5 Pro, Gemini 2.5 Flash and Gemini 3.5 Flash but not Gemini 3 Pro — [timewell.jp (third-party, 2026-09; not fetched, via search snippet)](https://timewell.jp/en/columns/vertex-ai-tokyo-region-data-residency-2026); contradicted by a blog claiming Gemini 3 Pro GA in 12 regions including asia-northeast1 as of May 2026 — [verdent.ai (third-party, unverified)](https://www.verdent.ai/guides/access-gemini-3-1-pro-vertex-ai)

### Inferences
- For "AI inside the boundary", the strongest contractual position for a Japanese SMB is Google-managed Vertex/Agent Platform (Google is sole data processor, Service Terms §18/§20 apply, billing on the existing GCP invoice). Picking Claude via Google-managed means choosing between **Sonnet 4.6 on a regional endpoint** (data residency, +10%) or **newer models on global/us/eu endpoints** (no Japan residency). Gemini 2.5 Flash/Pro in asia-northeast1 is the documented Japan-resident option today.
- Anthropic-managed on Google Cloud is attractive if the team wants Anthropic-native features (Managed Agents, Files/Batches), but it pulls data processing to Anthropic (US workspace geo) and so is a weaker fit for an IT advisor's "keep it inside Google" requirement.
- Token cost for a few thousand messages/month of classification/summarization on Haiku 5.5 or Gemini Flash is likely single-digit USD/month; the cost driver would be any agentic/long-context use.

- The Vertex AI data-governance page (abuse-monitoring logging period, zero-data-retention opt-out specifics for Gemini) and the Claude-on-Vertex region table (whether `asia-northeast1` is a Claude regional endpoint) are on `docs.cloud.google.com`, which was unreachable; no primary confirmation was obtained. - Whether Gemini 3.x models are GA in asia-northeast1 is unresolved (conflicting third-party claims; Google's own page not fetched).
- Vertex AI per-token prices for Claude/Gemini on Google's pricing page were not extracted (page redirects to `model-garden/pricing`, content not parsed).

## Key Question 3 — Security controls a non-IT company can actually turn on; PII (施主情報) risks

### Takeaway
Primary Google admin help pages were blocked, so edition-specific evidence is secondary: Context-Aware Access is reported **not** available on any Business edition (Enterprise/Cloud Identity Premium only), 2SV enforcement is available in the Admin console without a documented edition limit, and Drive DLP rules are listed for Business Standard/Plus. On the GCP side, the concrete, cheap controls are IAP on Cloud Run, IAM group bindings, Secret Manager (free at this scale) and the Service Terms no-training/no-retention clauses; Google Cloud's own guidance for IAP+Domain Restricted Sharing is designed exactly for internal apps.

### Cited Findings
- Context-Aware Access is **not** included in "all Business editions" (nor Frontline Starter, Essentials, Nonprofits); eligible editions are Enterprise Standard/Plus, Frontline Standard, Enterprise Essentials Plus, Education Standard/Plus and Cloud Identity Premium — [Venn help article (third-party), via search snippet](https://help.venn.com/hc/en-us/articles/14054031447067); similar list in [decryptiondigest (third-party)](https://www.decryptiondigest.com/blog/google-workspace-security-hardening)
- 2-Step Verification enforcement is configured under Admin console **Security > 2-Step Verification** with an enforcement start date; no source tied enforcement to an edition — [reco.ai guide (third-party), via search snippet](https://reco.ai/hub/google-workspace-2-step-verification); Google has required 2SV for Workspace admin accounts — [Yahoo/TechRadar report, via search snippet](https://malaysia.news.yahoo.com/google-workspace-admin-accounts-now-152437502.html)
- Google's DLP rules help page lists supported editions for label-applying DLP as "Business Standard and Business Plus; Enterprise Starter, Standard, Plus; Education Standard/Plus; Essentials…" and notes Drive DLP requires a license that includes Drive log events — [support.google.com/a/answer/9843931, via search snippet](https://support.google.com/a/answer/9843931); Google's edition comparison shows a "Drive DLP data protection insights report" row for Business Starter/Standard — [Compare Business editions (knowledge.workspace.google.com), via search snippet](https://knowledge.workspace.google.com/admin/getting-started/editions/compare-business-editions); a reseller summarises basic DLP for Starter/Standard and advanced DLP for Business Plus — [Flatiron Networks (third-party)](https://www.flatironnetworks.com/products/google)
- IAP on Cloud Run gives "authentication and authorization based on user or group identities, plus context-aware factors like IP address, geolocation, and device security status" and avoids granting `allUsers` invoker, which "was a blocker for … Domain Restricted Sharing organization policy"; Google Cloud does not charge for IAP in this setup — [Google Cloud blog (2026-03-13)](https://cloud.google.com/blog/products/serverless/iap-integration-with-cloud-run)
- Google Sign-In usage is subject to Google's API Services User Data Policy (Service Terms §41(b)) — [Service Specific Terms](https://cloud.google.com/terms/service-terms)
- Secret Manager: 6 active secret versions and 10,000 access operations/month free; $0.03 per 10,000 accesses thereafter — [Secret Manager pricing](https://cloud.google.com/secret-manager/pricing)
- Claude Code docs recommend, for the Claude side, a dedicated GCP project for cost tracking and access control, and the minimum IAM role `roles/aiplatform.user` (permission `aiplatform.endpoints.predict`), or a custom role with only that permission — [Claude Code on Google Cloud's Agent Platform](https://code.claude.com/docs/en/google-vertex-ai)
- LINE's own guidance: LINE platform IP addresses are not published, so webhook security must rely on signature verification, not IP allowlists — [LINE Developers tip "Always verify the signature" (2026-06-18), via search snippet](https://developers.line.biz/en/tips/2026/06/18/verify-webhook-signature/)

### Inferences
- A practical "turn-on list" for a 30-person company on Business Standard/Plus: enforce 2SV for all users; restrict Drive external sharing (official page not fetched — see gaps); put the app behind **IAP on Cloud Run bound to a Google Group** (`roles/iap.httpsResourceAccessor`); keep LINE/Teams/ANDPAD tokens in **Secret Manager**, mounted into Cloud Run via a dedicated service account with only `secretmanager.secretAccessor`; use Firestore in `asia-northeast1`; enable Cloud Audit Logs (Admin Activity is on by default; Data Access logs for Firestore are a one-click org/project setting — not verified in this session).
- PII minimisation for 施主情報: store the customer master in one place (ANDPAD or a Sheet/Firestore collection with restricted access), keep only 案件 IDs and status in the dashboard/Looker Studio data source, and never send raw customer identifiers to the LLM when classification only needs the message text. Both Google (Service Terms §18, §20(h)) and Anthropic (no-training, 30-day or ZDR) provide contractual cover, but the local risk is Drive over-sharing and Looker Studio reports shared "anyone with link".

## Key Question 4 — Claude Code in 2026: permission model, sandboxing, enterprise/cloud deployment (Vertex backend, managed agents, network policy), and guardrails for the "agent might break out and act on external systems" concern

### Takeaway
Claude Code's controls are layered and documented: (a) permission rules/modes (deny rules win in every mode, `disableBypassPermissionsMode`, `disableAutoMode`), (b) an OS-level sandbox for Bash (bubblewrap/Seatbelt) whose network allowlist starts **empty** and can be locked so only admin-managed domains apply, (c) managed settings that override user/project settings, and (d) cloud sessions in isolated VMs with default-limited egress. The docs themselves state that permission rules alone do not stop `curl`/`wget` if Bash is allowed — the sandbox network allowlist is what closes that gap — and that unattended runs must sit inside a container/VM. Running Claude Code against Google Cloud's Agent Platform keeps inference billing/governance in GCP, turns Anthropic telemetry off by default, and keeps `/feedback` bundles local.

### Cited Findings

**Permission model**
- Manual mode: Claude Code "starts with read-only permissions" and asks before edits/commands; a built-in set of read-only commands (`ls`, `cat`, `git status`) runs without asking; Auto mode (built-in starting mode for interactive terminal/VS Code) uses "a separate classifier model" that "blocks the ones it judges unsafe"; organizations can turn auto mode off — [Claude Code Security (code.claude.com)](https://code.claude.com/docs/en/security)
- Permission modes: `default` (Manual), `acceptEdits`, `plan`, `auto`, `dontAsk`, `bypassPermissions`; "Deny rules block in every mode, including `bypassPermissions`"; Auto became the built-in default for terminal/VS Code on all plans in v2.1.283; `claude -p`/SDK default to Manual (v2.1.302+) — [Permission modes](https://code.claude.com/docs/en/permission-modes)
- Auto-mode classifier blocks by default: "Downloading and executing code (`curl | bash`)", "Sending sensitive data to external endpoints", "Production deploys and migrations", "Force push", `git reset --hard`, `terraform destroy`, merging unapproved PRs, irreversible deletion of pre-existing files; after 3 consecutive or 20 total blocks it pauses and resumes prompting; entering auto mode drops broad allow rules like `Bash(*)` — [Permission modes](https://code.claude.com/docs/en/permission-modes)
- Rule syntax: `Bash(npm run *)`, `WebFetch(domain:example.com)`, `Read(./.env)` / `Read(./secrets/**)` deny rules; "A broad deny rule like `Bash(aws *)` blocks every matching call… An allow rule can't carve an exception out of a deny rule"; MCP tools can be denied with `mcp__*`; "Restrict Bash network tools: use deny rules to stop `curl`, `wget`… A deny rule doesn't match the same program by path or inside `sh -c`, so pair it with the sandbox network allowlist when the restriction must hold" — [Configure permissions](https://code.claude.com/docs/en/permissions)
- To prevent `bypassPermissions` or `auto` org-wide, set `permissions.disableBypassPermissionsMode: "disable"` / `permissions.disableAutoMode: "disable"` in managed settings; bypass is also refused when running as root/sudo unless inside a recognized sandbox — [Permission modes](https://code.claude.com/docs/en/permission-modes); [Configure permissions](https://code.claude.com/docs/en/permissions)
- "Network command approval: Commands that fetch content from the web such as `curl` and `wget` are not auto-approved by default"; "Command injection detection"; "Fail-closed matching: In Manual mode, unmatched commands require approval by default"; WebFetch returns a separate model's summary rather than the raw page for most fetches — [Security](https://code.claude.com/docs/en/security)

**Sandboxing**
- Enforced at OS level: Seatbelt (macOS), bubblewrap + socat (Linux/WSL2); native Windows unsupported; default off, enabled via `/sandbox` or `sandbox.enabled: true`; default writes limited to working dir + `$TMPDIR`; reads of the whole machine (incl. `~/.ssh`) allowed unless `denyRead`; protected paths (`.claude/settings*.json`, `.mcp.json`, `.git/hooks`, shell rc files) are always write-denied — [Sandboxing](https://code.claude.com/docs/en/sandboxing)
- Network: "The sandbox has no direct route out. Traffic goes through a local proxy that checks hostnames against the allowlist"; `allowedDomains` "starts empty"; tools that ignore proxy variables (plain `ssh`, DB drivers, UDP) cannot connect; hosts not in the allowlist prompt in Manual/acceptEdits, are refused in `dontAsk`, allowed in `bypassPermissions`; link-local/metadata addresses (`169.254.169.254`) are refused — [Sandboxing](https://code.claude.com/docs/en/sandboxing)
- Fail-open vs fail-closed: `sandbox.failIfUnavailable` (default `false` = commands run unsandboxed if the sandbox cannot start; `true` = exit at startup); `allowUnsandboxedCommands: false` = "strict sandbox mode" ignoring the `dangerouslyDisableSandbox` retry — [Sandboxing](https://code.claude.com/docs/en/sandboxing)
- Credential masking: `sandbox.credentials` can `deny` files/env vars (e.g., `~/.aws/credentials`, `GITHUB_TOKEN`) or `mask` them so the command sees a sentinel and the proxy injects the real value only for `injectHosts` (requires `network.tlsTerminate`) — [Sandboxing](https://code.claude.com/docs/en/sandboxing)
- Recommended enterprise lockdown (managed settings): `sandbox.enabled: true`, `failIfUnavailable: true`, `allowUnsandboxedCommands: false`, `network.allowManagedDomainsOnly: true`, `allowManagedReadPathsOnly: true`, `enableWeakerNestedSandbox: false`, `enableWeakerNetworkIsolation: false`, narrow `excludedCommands`; in "admin-required mode" repository `.claude/settings*.json` cannot add `excludedCommands`, `allowWrite`, `allowedDomains` or loosening flags (v2.1.282–284) — [Sandboxing](https://code.claude.com/docs/en/sandboxing)
- Isolation comparison: the per-command Bash sandbox does **not** cover MCP servers, hooks or plugin monitors ("run unconstrained on the host"); the `@anthropic-ai/sandbox-runtime` (`srt claude`) wraps the whole process; dev containers, custom containers, VMs and cloud sessions put everything inside the boundary; "Always run `--dangerously-skip-permissions` sessions inside a container, a VM, or the sandbox runtime"; "Any approach that allows network egress can still leak data the agent can read" — [Choose a sandbox environment](https://code.claude.com/docs/en/sandbox-environments)
- Reference dev container includes `init-firewall.sh` (requires `NET_ADMIN`/`NET_RAW`) limiting outbound traffic; warning: with `--dangerously-skip-permissions` "dev containers do not prevent a malicious project from exfiltrating anything accessible inside the container, including the Claude Code credentials stored in `~/.claude`"; avoid mounting `~/.ssh` or cloud credential files — [Development containers](https://code.claude.com/docs/en/devcontainer)

**Enterprise / managed settings / audit**
- Managed settings file paths: macOS `/Library/Application Support/ClaudeCode/managed-settings.json`, Linux/WSL `/etc/claude-code/managed-settings.json`, Windows `C:\Program Files\ClaudeCode\managed-settings.json`; plus plist/HKLM registry and server-managed (claude.ai admin console, highest priority; refreshed hourly); managed values "take precedence over user and project settings"; array settings like `permissions.deny` merge so "developers can extend managed lists but not remove from them" — [Set up Claude Code for your organization](https://code.claude.com/docs/en/admin-setup); [Deploy managed settings](https://code.claude.com/docs/en/managed-settings)
- Enforceable keys include `permissions.allow/deny`, `allowManagedPermissionRulesOnly`, `permissions.disableBypassPermissionsMode`, `permissions.defaultMode`/`disableAutoMode`, `sandbox.*`, `allowedMcpServers`/`deniedMcpServers`/`allowManagedMcpServersOnly`, `strictKnownMarketplaces`, `allowManagedHooksOnly`, `allowedProviders` (v2.1.285+), `availableModels`/`enforceAvailableModels`, `maxEffortLevel`, `minimumVersion`, and telemetry opt-out via `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` — [Set up Claude Code for your organization](https://code.claude.com/docs/en/admin-setup)
- "Permission rules and sandboxing cover different layers. Denying WebFetch blocks Claude's fetch tool, but if Bash is allowed, `curl` and `wget` can still reach any URL. Sandboxing closes that gap with a network domain allowlist enforced at the OS level." — [Set up Claude Code for your organization](https://code.claude.com/docs/en/admin-setup)
- Team-security recommendations: managed settings, share approved permission configs via version control, monitor via OpenTelemetry metrics, and "Audit or block settings changes during sessions with `ConfigChange` hooks" — [Security](https://code.claude.com/docs/en/security)
- Organization model/effort restrictions set in claude.ai admin do **not** reach Bedrock/Agent Platform/Foundry sessions; use managed settings (`availableModels`, `model`, `maxEffortLevel`) there — [Set up Claude Code for your organization](https://code.claude.com/docs/en/admin-setup)

**Vertex (Agent Platform) backend and data flow**
- Setup: `CLAUDE_CODE_USE_VERTEX=1`, `CLOUD_ML_REGION=global|us|eu|<region>`, `ANTHROPIC_VERTEX_PROJECT_ID`; model access requested in Model Garden ("may take 24-48 hours"); default primary model `claude-opus-5-5`, small/fast `claude-sonnet-4-5@20250929`; pin models with `ANTHROPIC_DEFAULT_*_MODEL`; `/login` wizard "Google Vertex AI"; `CLOUD_ML_REGION` falls back to `us-east5`; prompt caching on by default; IAM `roles/aiplatform.user` — [Claude Code on Google Cloud's Agent Platform](https://code.claude.com/docs/en/google-vertex-ai)
- On Agent Platform, metrics, error reports and `/feedback` are **off by default**; `/feedback` writes a redacted bundle to `~/.claude/feedback-bundles/` instead of uploading; encryption at rest "Google-managed encryption keys. CMEK available"; the Development Partner (training) program "is not available for … Google Cloud's Agent Platform users"; commercial users: "Anthropic does not train generative models using code or prompts sent to Claude Code under commercial terms"; standard retention 30 days (first-party) — [Data usage](https://code.claude.com/docs/en/data-usage)
- Cloud sessions (claude.ai/code): "Each cloud session runs in an isolated, Anthropic-managed VM"; "Network access is limited by default and can be configured to be disabled or allow only specific domains"; GitHub credentials never enter the VM (proxy attaches them server-side); proxy "rejects branch deletions and pushes of anything other than a branch"; "All operations in cloud sessions are logged"; self-hosted environments put isolation/egress on the customer — [Security](https://code.claude.com/docs/en/security); cloud environments support network access levels, environment variables, network secrets and setup scripts; organization-shared environments set by Owners — [Configure cloud environments](https://code.claude.com/docs/en/cloud-environments)

### Inferences
- Answering the IT advisor's "break out and act on external systems" concern, in order of strength: (1) run Claude Code in a **dev container/VM with a default-deny egress firewall** (reference `init-firewall.sh`) or the sandbox runtime; (2) enable the built-in sandbox with `failIfUnavailable: true`, `allowUnsandboxedCommands: false`, `allowManagedDomainsOnly: true` and an allowlist limited to `aiplatform.googleapis.com`, `github.com`, package registries; (3) managed `permissions.deny` for `Bash(curl *)`, `Bash(wget *)`, `Bash(gcloud run deploy *)`, `Bash(gcloud * --project=prod*)`, `Read(./.env)`, `Read(~/.config/gcloud/**)`, plus `disableBypassPermissionsMode`; (4) give the agent only **read-only / dev-project** credentials (a service account with viewer roles, LINE/Teams **test** channels, ANDPAD sandbox or read-only token) and mask real tokens via `sandbox.credentials`; (5) require deploys to go through a reviewed PR + CI (Cloud Build/GitHub Actions) that the agent cannot trigger directly, i.e., the agent writes code and dry-run plans, humans press "deploy".
- Using Agent Platform as the backend answers the "data stays in Google" requirement for the coding assistant itself: prompts/outputs are processed by Google-managed Claude, Anthropic telemetry is off, and billing/IAM/audit are in the company's GCP project. The trade-off is losing claude.ai-only features (cloud sessions, Code Review) unless Team/Enterprise seats are also bought.
- The docs are explicit that the Bash sandbox alone is insufficient for unattended runs; the architecture spec should state that any `--dangerously-skip-permissions`/auto-mode runs happen only inside a container with egress limits.

## Key Question 5 — Webhook mechanics for LINE and Microsoft Teams (signature verification, timing, 2025–2026 retirements) and ANDPAD data access

### Takeaway
LINE webhooks must be verified with HMAC-SHA256 over the **raw body** using the channel secret, compared against the base64 `x-line-signature` header (LINE publishes no IP ranges). Teams has two different inbound mechanisms: **outgoing webhooks** (HMAC over the body with a per-webhook token in `Authorization: HMAC …`, but channel-only and require an @mention; response window stated as 5 s on one Microsoft page and 10 s on another) and **Workflows (Power Automate)** triggers; **Office 365 connectors (incl. connector-based incoming webhooks) were retired in May 2026** per Microsoft's docs note. ANDPAD exposes an API through its アプリマーケット partner program, but no public developer documentation or self-serve terms were found.

### Cited Findings

**LINE Messaging API**
- Signature: LINE generates HMAC-SHA256 using the channel secret as key over the request body and sets it (base64) in the `x-line-signature` header; verify before processing; modifying body or signature before verification causes failure — [Verify webhook signature (developers.line.biz), via search snippet](https://developers.line.biz/en/docs/messaging-api/verify-webhook-signature/); [Japanese version](https://developers.line.biz/ja/docs/messaging-api/verify-webhook-signature/)
- LINE's 2026-06-18 developer tip: "Always verify the signature on your Messaging API webhooks"; LINE platform IPs are not published, so IP-based access control is not an option — [LINE Developers tip (2026-06-18), via search snippet](https://developers.line.biz/en/tips/2026/06/18/verify-webhook-signature/)
- Webhook URL verification: design the endpoint to return 200 to LINE's verification POST — [Verify webhook URL, via search snippet](https://developers.line.biz/en/docs/messaging-api/verify-webhook-url)
- Official Node SDK (`@line/bot-sdk`, Node ≥22): `validateSignature(body, channelSecret, signature)` computes `createHmac("SHA256", channelSecret)` over the body and compares to the base64-decoded signature with `timingSafeEqual`; `middleware(config)` must run **before** any body parser ("needs the raw body"); missing/mismatched signature raises `SignatureValidationFailed` (example responds 401); webhook URL must be HTTPS — [line-bot-sdk-nodejs validate-signature.ts (GitHub)](https://github.com/line/line-bot-sdk-nodejs/blob/master/lib/validate-signature.ts); [webhook guide (GitHub)](https://github.com/line/line-bot-sdk-nodejs/blob/master/docs/guide/webhook.md); [README](https://github.com/line/line-bot-sdk-nodejs/blob/master/README.md)

**Microsoft Teams**
- Outgoing webhook: acts as a bot responding to @mentions in team channels; callback must be an HTTPS endpoint accepting JSON; Teams generates an HMAC security token that "doesn't expire and is unique for each configuration"; the HMAC is sent in the `Authorization` header with the `HMAC` scheme; verification = HMAC-SHA256 over the UTF-8 request body using the base64-decoded token, compared to the header; "your code has five seconds to respond"; scoped to the team, requires @mention, public channels only; cannot call other Teams APIs; card actions limited to `openURL` — [MicrosoftDocs/msteams-docs add-outgoing-webhook.md (GitHub mirror of learn.microsoft.com)](https://github.com/MicrosoftDocs/msteams-docs/blob/main/msteams-platform/webhooks-and-connectors/how-to/add-outgoing-webhook.md)
- The overview page instead says the service "has 10 seconds to reply" for outgoing webhooks — **conflict** with the 5-second figure above — [what-are-webhooks-and-connectors.md (GitHub mirror)](https://github.com/MicrosoftDocs/msteams-docs/blob/main/msteams-platform/webhooks-and-connectors/what-are-webhooks-and-connectors.md)
- Microsoft's docs deprecation note: "Office 365 Connectors in Teams, including connector-based Incoming Webhooks, were retired in **May 2026**"; replacement is the **Workflows** app (templates, or a custom workflow with the "When a Teams webhook request is received" trigger), Power Automate connectors, or an updated Teams app — [msteams-docs includes/deprecation-note.md (GitHub mirror)](https://github.com/MicrosoftDocs/msteams-docs/blob/b186b6ef467cdf8ba5351cc20f0995565be8cb78/msteams-platform/includes/deprecation-note.md). Earlier Message Center snapshots (MC808160, 2024) had said connectors would be retired "in December 2025" with URL updates due by Jan 31, 2025 — [mc.merill.net mirror of MC808160](https://mc.merill.net/message/MC808160/v/2024-08-20T17-33-10-81Z)
- Incoming webhook via Workflows: template "Send webhook alerts to a channel"; POST JSON like `{"text": "..."}` to the generated URL; 28 KB message limit; throttling above four requests per second — [add-incoming-webhook.md (GitHub mirror; `ms.date` 10/26/2026)](https://github.com/MicrosoftDocs/msteams-docs/blob/main/msteams-platform/webhooks-and-connectors/how-to/add-incoming-webhook.md)
- Microsoft's Node sample repo for outgoing-webhook HMAC exists but the `app.js` path returned 404 at fetch time — [OfficeDev/msteams-samples-outgoing-webhook-nodejs](https://github.com/OfficeDev/msteams-samples-outgoing-webhook-nodejs); a C# sample `AuthProvider.cs` is referenced in search results — [OfficeDev C# sample (via search snippet)](https://github.com/OfficeDev/microsoft-teams-sample-outgoing-webhook)
- Third-party guidance: scripts should call an HTTP-triggered Power Automate flow which posts to Teams; the flow can sit behind API Management or Entra authentication; DLP policies may block some connectors — [mundobytes (third-party, via search snippet)](https://mundobytes.com/como-enviar-alertas-a-teams-y-slack-desde-scripts-con-webhooks-seguros/)

**ANDPAD**
- ANDPAD operates an "ANDPADアプリマーケット", described as a platform that "ANDPAD APIの提供を通じ" connects construction companies with IT vendors/developers; first batch of 12 partner integrations announced — [ASCII.jp (via search snippet; article not fetched)](https://ascii.jp/elem/000/004/074/4074433/); StrategIT's "eセールスマネージャー to ANDPAD" states "公開APIを利用し当社独自で運営" — [ASCII.jp (via search snippet)](https://ascii.jp/elem/000/004/099/4099927/)
- ANDPAD job postings list "連携ソリューションの設計・開発（Open API、連携機能の整備）" — [HERP Careers (via search snippet)](https://herp.careers/careers/companies/andpad/jobs/h4-cmrf0m70100782e0gfbvnrov2)

### Inferences
- A Cloud Run webhook service should expose `/webhooks/line` (raw-body HMAC-SHA256 with channel secret from Secret Manager, respond 200 fast, enqueue processing) and `/webhooks/teams` (either outgoing-webhook HMAC verification with the per-webhook token, or a Power Automate "When a new channel message is added" → HTTP action with a shared secret header, since outgoing webhooks require @mention). Given the 5 s/10 s Teams window and LINE's expectation of a prompt 200, processing should be async (Cloud Tasks/Pub/Sub or Firestore write + scheduled job).
- Because ANDPAD API access appears to be partner-gated, the architecture should assume an **export/CSV or manual-sync fallback** (Drive upload → Cloud Run importer) until API credentials are obtained; a separate research note (`andpad_api.md` in this folder) may cover ANDPAD in more depth.

- Teams: the authoritative 5 s vs 10 s response window is unresolved; the Power Automate HTTP-trigger security options (Entra auth, IP restrictions) were not verified from Microsoft docs.
- ANDPAD: no developer documentation, application procedure, pricing, or rate limits were found.
